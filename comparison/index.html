    When to use Meta-Evolve¶

    Use Meta-Evolve to apply, compose, and evolve improvement methods through a common Python programming model. It is useful when your work spans different artifacts, algorithms, or stages: software optimization, agent development, research procedures, and methods you build for scientific discovery.

    You define what can change and how it will be evaluated. The library provides artifact contracts, replaceable components, bounded execution, explicit experience, and inspectable results. The method library identifies runnable implementations and proposed research mappings.

    Choose a path¶

    You want to… Start with
    Apply a method to your problem Available methods, with setup and implementation scope
    Build a variant from compatible components Compose a method and compare the method structures
    Improve the procedure itself AutoResearch or policy evolution
    Develop a discovery method in your own domain Artifact domains and scientific method mappings

    Why use a common method framework?¶

    • Reuse work across methods. Keep a task, evaluator, artifact representation, or proposer when a compatible method can use it. The method worksheet makes those boundaries explicit. Full algorithms may need different stage schedules; changing a search preset alone does not implement them.
    • Represent the thing you actually improve. Source trees, skill collections, harnesses, and policy values have different structure and valid edits. Built-in and custom domains give those distinctions a contract without changing the coordinator.
    • Build methods with several stages. The AutoData lab composes generation, two solver conditions, acceptance checks, and recipe rewriting. Its current live integration and explicit Python orchestration demonstrate a bounded mechanism, not a packaged reproduction of the paper.
    • Evaluate an improvement procedure. AutoResearch makes a recipe the candidate and judges it through bounded inner runs. The outer result links the procedure to the outcomes used to measure it.
    • Inspect the evidence and work behind a choice. Recorded experience shows which prior observations were supplied; run inspection retains results and failures. Configured durable storage keeps committed history across processes.

    These controls support comparisons without making them fair automatically. Keep datasets, objective meanings, model settings, and resource units comparable, and report actual usage and incomplete runs. Equal evaluation allowances need not mean equal model calls or cost.

    What do I need to supply?¶

    For the simple callable path, supply a starting artifact, a function proposing revisions, and an independent evaluator. The complete parser tutorial defines all three; routing prompts and harness improvement show other artifacts. improve() adds bounded greedy search; Experiment exposes other search choices. The programming model owns that API.

    For a method, follow its walkthrough's setup and stage schedule. Your callables own the model or tool integration, domain execution, grading, and usage reports. No model is bundled. Start with Use your model SDK for provider wiring. If a supplied optimizer already fits your task, its built-in proposal and execution strategy can save you that work.

    Which tool fits my task?¶

    These choices overlap. The guidance below compares authoring responsibilities, not optimization quality. External descriptions come from the linked primary sources; they were not validated by running those systems. The source record dates and scopes each check.

    Meta-Evolve: apply, compose, and evolve methods¶

    Supply a seed, proposer, evaluator, and limits. The library supplies versioned artifacts, search presets, explicit feedback controls, and inspectable run records. Configure durable storage and reconstructible components when you need persistence and recovery. This suits experiments where you want to replace or study those components; it also leaves you responsible for the proposal strategy, SDK wiring, and grading. The package is Apache-2.0 licensed. Use the method library to choose a starting point and the shipped contract to extend it. Scientific method mappings are Design—not shipped; their proposed algorithms are not bundled implementations.

    When an improvement procedure becomes the candidate, evaluation, work limits, and promotion remain outside candidate authority. Search selects a measured result; deploying it is a separate decision. These are experiment contracts: process confinement depends on the execution environment, and an ordinary in-process Python callable is not a sandbox.

    DSPy: optimize LM programs¶

    Supply a DSPy program, a metric, training examples, and model configuration; choose an optimizer. DSPy provides the program abstractions and optimizers for instructions, demonstrations, or model weights, depending on the optimizer. If your application already uses DSPy, its own optimization path is a natural starting point. You still design the program and evaluation data. Using its outputs in Meta-Evolve would require your own integration. DSPy optimizer documentation.

    GEPA / OptimizeAnything: optimize with selectable engines¶

    Supply an evaluator and a seed or objective, plus model/engine configuration and work limits. Supply development and validation examples when optimizing across inputs. OptimizeAnything provides an optimization entry point with selectable engines; the GEPA engine supports reflective proposals and configurable candidate selection. Current APIs also expose custom proposers, saved evaluation records, and engines including autoresearch and meta_harness. It can reduce setup when a supplied engine fits; check the chosen engine's controls and output semantics against your needs. API, configuration, and candidate selection.

    OpenEvolve: evolve programs¶

    Supply an initial program, an evaluator, model configuration, and iteration limits. OpenEvolve provides model-driven program revision, population search using islands and diversity dimensions, and history visualization. Its library entry points can accept inline code; separate files are not always required. Consider it when that program-evolution workflow fits. You still author the grader, prepare its runtime, and choose the search configuration. OpenEvolve's maintained README.

    Meta-Harness: revise harness programs¶

    The paper describes a coding-agent proposer inspecting prior harness code, scores, and execution traces in a filesystem. Applying the method requires a task harness, task data and reward function, model access, and an execution environment. It is relevant when the procedure around a model is what you want to change. This describes the paper's method, not a verified general-purpose installation path. Our Meta-Harness example is a bounded mechanism demonstration, not a reproduction of its system or results. Meta-Harness §3 and Algorithm 1.

    Self-improving agents¶

    These papers study changes to agents or their improvement machinery. Their mechanisms help identify what a Meta-Evolve experiment would need to supply.

    Work What changes and how it is judged Local connection
    Darwin Gödel Machine (DGM) Agent code is revised and tested; valid self-editing variants enter an archive. Archive management and parent selection stay fixed. Proposed DGM mapping
    Huxley-Gödel Machine (HGM) Branch expansion uses estimated descendant productivity; evaluation allocation is a separate decision. Proposed HGM mapping, including the gap from TreeSearch
    Red Queen Gödel Machine Learned evaluators can change between epochs with fixed scoring rules; an independent anchor judges replacements. Evaluator governance and its limits

    DGM and HGM mappings remain Design—not shipped. Red Queen is a research precedent for the narrower #251 proposal. These connections supply neither runnable integrations nor performance evidence.

    AlphaEvolve: algorithm discovery¶

    DeepMind describes a system combining Gemini-generated programs, automated evaluation, and evolutionary selection. Formulating a problem with an executable quality measure is central to that approach. Its reported discoveries are useful research context; the announcement does not establish a currently available self-service setup or its authoring requirements, so this page makes no access recommendation. DeepMind's announcement.

    What do Meta-Evolve's guarantees mean for my run?¶

    Does it automatically save results or recover after a crash?¶

    Default local runs use in-memory storage. Pass Storage.durable(path) to save committed history for reopening and inspection. Resuming execution additionally requires a supported mode and registered, reconstructible components; persisting ordinary notebook callables does not make them resumable. See saving and recovery.

    Does replay call the model again?¶

    No. Replay reconstructs recorded facts without invoking proposers or evaluators. A fresh stochastic model call can produce a different answer; stored records do not promise identical regeneration. See run history.

    Is a spending limit a hard cap?¶

    No. The engine counts trials and evaluations and aggregates usage reported by your components. A monetary ceiling is enforced after reported charges: a call can exceed it before further work stops. Unknown billed spend stays unknown. The engine cannot verify a wrapper's billing report. See money and enforcement.

    Can candidate code change its own grader?¶

    The declared evaluator, budgets, and promotion rules remain outside candidate authority. However, ordinary local Python execution is not process isolation. Running untrusted code requires an appropriate execution boundary; see the source execution guide.

    Does it automatically use feedback or run evaluations in parallel?¶

    Feedback is explicit and off by default; the feedback guide shows how to supply it. Execution is serial by default; distributed mode supports explicit worker process backends. See execution profiles for supported controls and restrictions.

    Can I combine it with another optimizer?¶

    You can implement a callable that invokes another optimizer and returns a candidate, but that is integration work. Define artifact conversion, aggregate inner usage, handle failures, and keep selection data separate from final checks. No DSPy or OpenEvolve adapter is shipped. Our DSPy, GEPA, and OpenEvolve mappings identify remaining work; similar interfaces do not establish compatibility or reproduce an algorithm.

    What evidence supports improvement claims?¶

    The parser scores come from independently grading handwritten revisions. They teach execution and selection, not model performance. Historical provider captures are listed with their limits in the evidence index. The release quickstart's live report belongs to #271; no retained report was attached as of 2026-09-16. A negative result is still evidence.

    This comparison reports no head-to-head benchmark or broad superiority. Any future live claim must link the retained report and its exact configuration, baseline, failures, resource use, and final evaluation. A small demonstration cannot establish general performance.

    For the research question of recursive self-improvement, see the survey and mechanism map.

    Where do I start?¶

    Run the parser tutorial, then replace its starting value, revision function, and measurement function for your own task. Choose a task guide for feedback, limits, or saving; an application for a larger example; or the API reference for parameters and return values.
