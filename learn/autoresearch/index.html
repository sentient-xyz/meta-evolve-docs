    Build an autoresearch loop with Meta-Evolve¶

    What it does. This autoresearch example improves a recipe for conducting small searches, judging a recipe by the solutions those searches find.

    How it works. An outer loop revises the allowed moves for inner number searches. Public results guide revisions, private aggregate scores select a recipe, and held-out tasks check the selection. Tasks and limits stay fixed.

    Status: Shipped. Offline; optional next step after your first run.

    Component worksheet¶

    Question This method
    What changes? A Text JSON recipe declaring the moves an inner researcher can try.
    What generates the change? A deterministic proposer follows declared recipe successors using public feedback; each recipe configures the inner number proposer.
    What judges it? Fixed inner tasks produce private aggregate quality; outer Greedy selects on that metric.
    What is retained? An outer Run with recipes, public reports, private metrics, derivation, and outer usage. The final held-out report is produced separately.

    Inspired by AIDE², this is no reproduction or evidence of recursive self-improvement; promotion is external.

    The two levels¶

    “Inner” and “outer” describe which thing is being improved:

    outer Meta-Evolve run
│
├─ artifact: a recipe for conducting inner research
├─ proposer: one declared recipe revision
├─ evaluator: fixed tasks and budget ceilings
└─ search: select using private aggregate quality
       │
       ├─ inner run on public task A
       ├─ inner run on public task B
       ├─ inner run on private task A
       └─ inner run on private task B

report(result), after outer selection
├─ seed researcher on held-out tasks
├─ selected researcher on the same held-out tasks
└─ report the comparison; promote nothing

    An inner run searches for an integer near a target. The recipe determines its move sequence: (1,) takes single steps; (1, 2, 4) tries larger jumps within the same four-proposal ceiling. All outer attempts remain recorded.

    In meta-evolution notation, the recipe is θ, the bounded researcher is Iθ, and private aggregation is E_outer. Replace the integer task with your domain and its independent checks.

    The five Meta-Evolve declarations¶

    The canonical module's run_outer uses the ordinary public API:

    main.py · run_outer
    def run_outer() -> meta.Run:
    """Optimize the inner researcher under evaluator-owned selection."""

    experiment = meta.Experiment(
        task=meta.Task(
            evaluator=evaluate_researcher,
            artifact=meta.Text,
            objectives=(meta.Maximize("private_quality"),),
            budget=OUTER_BUDGET,
        ),
        seed=SEED,
        proposer=propose_researcher,
        search=meta.Greedy(max_trials=OUTER_TRIALS),
        context=meta.AncestorsOnly(max_records=CONTEXT_RECORDS),
        random_seed=0,
    )
    return meta.run(experiment)

    Read it as a sentence: Task fixes evaluation and limits; SEED is the starting recipe; propose_researcher proposes a successor; Greedy selects by private quality; and AncestorsOnly supplies authorized parent-lineage records.

    The outer run records candidates, metrics, hypotheses, evidence, derivation references, and outer usage. Its proposer filters the supplied records for public reports; the raw trusted context also contains private aggregate metrics.

    The candidate-controlled surface¶

    The complete mutable artifact is tiny JSON:

    {"moves":[1,2,4]}

    decode permits only the moves key, one to four integer moves, and values between 1 and 8. An invalid recipe produces a typed InvalidOutput with no metric, so malformed output can never outrank a valid researcher.

    import meta_evolve as meta

outcome = lab["evaluate_researcher"](meta.Text('{"moves":[0]}'))
print("failure:", type(outcome.failure).__name__)
print("metrics:", dict(outcome.metrics))
    Output
    failure: InvalidOutput
metrics: {}

    The declared owners are:

    Control Owner
    Move recipe Candidate
    Public, private, and held-out tasks Evaluator
    Inner and outer budgets Experiment
    private_quality calculation Evaluator
    Greedy admission Search policy
    Whether a winner is deployed Governance / user

    These are in-process Python fixtures. Candidate data is validated; actual execution isolation is a separate authority boundary.

    One candidate evaluation¶

    evaluate_researcher first validates the recipe. It then performs four inner runs under the same protocol and budget ceilings. Each task has its own target, and the recipe changes proposal behavior. The source is extracted here:

    main.py · evaluate_researcher
    def evaluate_researcher(candidate: meta.Text) -> EvaluationResult:
    """Select on private quality while exposing only public task traces."""

    try:
        researcher = decode(candidate)
    except (json.JSONDecodeError, ValueError) as error:
        return EvaluationResult(failure=InvalidOutput(message=str(error)))
    public = score(researcher, PUBLIC_TASKS)
    private = score(researcher, PRIVATE_TASKS)
    return EvaluationResult(
        metrics={"private_quality": fmean(private.values())},
        evidence=(
            EvidenceDraft(
                kind=PUBLIC_REPORT,
                data={"scores": public, "inner_trials_per_task": INNER_TRIALS},
            ),
        ),
    )

    Public per-task outcomes become inspectable evidence. Private task names, targets, and per-task outcomes are not placed in evidence. The outer search policy uses their aggregate metric for selection.

    The deterministic proposer extracts only autoresearch-public-report records. Its ProposalResult.derived_from points to the report it used. That records the declared basis of the revision; a citation alone does not prove benefit.

    score() reduces each in-memory inner run to a quality value. The outer report does not retain reopenable inner IDs, full inner histories, or captured partial episode outcomes. The policy example shows those additional retention choices.

    Exact budget arithmetic¶

    The seed and two successors give the outer run:

    3 outer evaluations = 1 seed + 2 proposals
2 outer trials      = 2 proposals

    Each outer evaluation runs four tasks. Each permits the seed plus four inner proposals, but stops early if it reaches the target:

    5 inner evaluations per task
× 4 tasks per outer evaluation
× 3 outer evaluations
= 60 inner evaluations used for selection at most

    After selection, the seed and winner each run on two held-out tasks:

    5 × 2 recipes × 2 held-out tasks = 20 post-selection evaluations at most

    These are ceilings, not equal consumed work. The outer budget counts outer evaluations; this evaluator does not forward inner usage in EvaluationResult. Outer usage therefore does not measure total nested cost. An adaptation that needs physical cost comparisons must explicitly report that usage.

    report(result) performs the held-out executions and formats their scores. They are not attached to the original outer Run; calling report() again executes them again. Keep a final comparison separate from further search.

    Why three task splits?¶

    The public tasks provide feedback for proposing the next researcher. The private aggregate decides which recipe is selected. Held-out tasks are touched only after the search has selected a winner.

    Split Candidate model may see details? Affects selection?
    Public Yes Indirectly, through proposals
    Private No Yes, through aggregate quality
    Held-out No during search No

    If the outer model sees private targets or per-task results, “private” is only a label. If held-out results influence another proposal, those tasks have become part of development and a new untouched suite is required.

    Replacing the deterministic proposer with an agent¶

    The deterministic proposer keeps CI credential-free. A model-backed wrapper should preserve this boundary:

    ProposerContext → allowlisted public evidence → private workspace
  → one bounded agent session → validated ProposalResult
  → derived_from references and usage

    Do not give the model raw outer context because it contains the aggregate private metric needed by trusted search. Build an allowlisted workspace. The prompt-optimization example shows how a callable outer proposer can run a bounded source-tree agent one level down and lift the result back into meta.Text.

    For a source-code researcher, change the artifact to meta.SourceTree, use an exact mutation allowlist, and evaluate each candidate in a fresh workspace. Keep benchmark source, credentials, permissions, and promotion controls outside that tree.

    What the comparison may claim¶

    Under these toy tasks and equal inner budget ceilings, the selected recipe has higher private and held-out quality than the seed.

    It does not establish real-domain autonomy, superiority to experts, statistical robustness, out-of-distribution generalization, accelerating improvement, reward-hacking safety, or readiness for automatic deployment.

    Those claims require larger protocols, repeated runs, fixed physical costs, external baselines, untouched tasks, and adversarial checks. Negative results, ties, typed failures, and rejected proposals must remain in the record.

    Relationship to M8¶

    This historically pre-M8 example composes meta.Text, nested meta.run, evidence, lineage, budgets, and ordinary search. It adds no production runtime.

    M8 now supplies HarnessArtifact, MutationSurface, portable episode suites, strict held-out comparison, and safe export. This chapter stays as the explicitly small recipe-evolution composition; the canonical harness story is the M8 guide.

    Leakage and validity checklist¶

    1. Can candidate code read private task files, environment variables, grader output, or prior held-out results?
    2. Are baseline and candidate evaluated on exactly the same tasks, seeds, model identity, tool permissions, and physical budget?
    3. Can a candidate increase concurrency, retries, context, or model calls and thereby buy a better score?
    4. Are malformed output, timeout, policy violation, and infrastructure failure unrankable typed outcomes rather than zeros?
    5. Does every proposal identify the public evidence it actually used?
    6. Is held-out evaluation run once after selection and excluded from promotion unless promotion policy explicitly owns it?

    Change and predict¶

    Change INNER_TRIALS from 4 to 2, update INNER_BUDGET consistently, and predict which recipe wins before rerunning the example. Then ask whether the winner changed because its research strategy is generally better or because the experiment changed the resource regime.
