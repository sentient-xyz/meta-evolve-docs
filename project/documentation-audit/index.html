    Documentation audit and editorial conventions¶

    Lead with improving solutions and the methods that produce them. The use, compose, and evolve journeys connect that idea to implementations and research directions. The complete duration parser teaches the common API; task guides and examples provide next steps. Keep instructions beside code and evidence.

    Ownership and navigation¶

    Section Reader's question Content owner
    Start What can I improve, and how do I begin? Homepage overview and First experiment parser walkthrough
    Guides How do I change one part of an experiment? Evaluation, proposal, search, feedback, limits, storage, and composition
    Examples How does this apply to my problem? One catalog of maintained runnable examples
    Concepts Why does it work this way? Explanations under the architecture contract
    Reference What does this API accept and return? Source signatures, detailed contracts, tools, programming model, and the complete command inventory
    Development (secondary) What exists, and how do I contribute? Contribution routes, contracts, status, roadmap, research map, design and evidence indexes

Keep historical URLs or explicit redirects when moving their navigation entries. Source repair, integer demonstrations, and evidence notebooks are additional examples rather than competing introductions.

    Development links to indexes and canonical overviews; detailed designs and historical notebooks remain accessible at their existing URLs. Examples owns runnable methods and applications, grouped by what changes and how it is judged. The parser's primary next step is live SVG Feedback Descent; adaptation guides, the live parser, and the gallery provide alternatives. Keep one navigation home per page and avoid an automatic footer that contradicts the tutorial's next step.

    Open the programming model with the mental model and callable API. Ordinary guides and concepts explain current behavior without milestone chronology; project status and evidence records retain development history. Preserve decision-relevant limitations beside the behavior they qualify. Navigation checks protect reader routes and historical destinations, not an exact submenu layout or leaf count.

    The homepage has three blocks: an introduction to broad artifact improvement and improving the method itself, a canonical parser declaration with its measured result, and selected examples. Keep the proposer’s handwritten behavior and its agent/LLM replacement point clear in the shared code comments. Link the primary action to the complete parser tutorial; feature SVG Feedback Descent, EvoSkill, and Meta-Harness in that order, followed by the example catalog. These are a selection, not permanent categories. Keep setup, availability, authentication, and development details on their substantive pages.

    The tutorial and README retain installation, every definition, one handwritten revision, independent evaluation, and verified output. The homepage includes only the canonical improve declaration; literal README cells and shared setup are checked against their owners. Execute the excerpt with the canonical definitions and test the full tutorial outside the checkout with the installed package. Keep the notebook export complete and runnable.

    The programming model owns the shipped API; architecture owns domain semantics; milestones owns scope and acceptance gates; and the implementation plan owns technical staging. Design records remain subordinate, including records whose decisions later shipped.

    Comparisons and positioning¶

    The comparison explains method reuse, structured artifacts, composition, and evaluating improvement procedures through concrete examples. It answers fit, authoring responsibilities, and next steps. Support external capability claims with versioned primary sources, check dates, and the material actually inspected. Name uncertainty instead of inferring absence; preserve unrelated source dates. Compare complete setup and responsibilities, not call-site argument counts. Qualify storage, recovery, accounting, and execution guarantees beside their benefits. Live performance claims must link retained evidence; tutorial scores remain teaching evidence. Conceptual roles, availability, autonomy, and strength of evidence answer different questions. Keep the survey's attributed autonomy map on its research page. Distinguish empirical evidence, conditional proofs, and bias-relative search guarantees; a practical estimator does not inherit an idealized oracle's guarantees. Keep historical comparison anchors.

    Method walkthroughs¶

    The gallery at examples.md owns discovery of runnable methods and applications. It shows the editable artifact, evaluation, and a brief execution requirement; the walkthrough owns detailed setup and commands. The complete script inventory lives at reference/example-commands.md. The research map at research/index.md owns proposed mappings and adjacent references under Development. Keep one canonical walkthrough per method and preserve retired catalog URLs through substantive redirects. Keep availability aligned with research/catalog.json; use only Shipped, Experimental/live-only, and Design—not shipped as status labels.

    Open every algorithm or method page with a short What it does. and How it works. summary before setup, component tables, or implementation details. Explain the problem, the changing object, and the distinctive mechanism in plain language, so the paper is optional reading. Cite the primary source for research claims and distinguish its method from this repository's adaptation or proposal. For surveys, benchmarks, and infrastructure references, describe their contribution without pretending that each is an optimization algorithm.

    Keep that orientation consistent while preserving the method's teaching order: SVG shows drawing and critique; EvoSkill makes direct agent calls before search; Meta-Harness measures a harness through fresh repairs. Preserve captured outcomes and code provenance. Prose-only changes must not invalidate or silently replace live evidence; code changes require the existing capture-validity checks.

    SVG is a live walkthrough. Introduce Feedback Descent and link the Stanford blog before setup. Show the ask input/output boundary so readers can use their own agent; explain revise and grade alongside their code. Keep required helpers expanded, optional display code collapsed, and the captured images as supporting evidence. Exercise replacement agents without making billable calls in tests.

    After the problem, answer the four method questions: what changes, what generates the change, what judges it, and what is retained? Name fixed controls and actual stages, including search and feedback. Keep exact algorithm scope, complete setup, supported execution, result interpretation, adaptation, and evidence together. Identify whether the candidate is an output, generator, policy, or research procedure.

    State which results are returned, persisted, or produced by later calls. Capturing inner histories and forwarding physical usage are explicit choices; nesting supplies neither automatically. The nested-evaluation comparison shows the different policy and AutoResearch boundaries. An outer Run need not capture or resume the whole method.

    Implementation scope and evidence are separate from availability. Preserve the distinction between a mechanism fixture, live integration, and a reproduction. A search preset does not establish a complete research method. Scientific discovery belongs in the framework's application scope, while unimplemented scientific methods retain their Design—not shipped status. New method releases update the canonical walkthrough, catalog, source/download links, and evidence together; composition claims point to code showing actual compatible reuse. State authentication and platform needs separately from status. Distinguish live-capable code, offline SDK rehearsal, and a retained live capture, and identify the tested source/package through the existing evidence records. Publish package, support downloads, and documentation as one verified build; a working local download path is not evidence of public availability.

    Concept conventions¶

    Concepts start with the duration parser. Offer the path: improvement loop → artifacts → meta-evolution → evaluation and authority → experience → deeper semantics. Keep search, history, budgets, failures, identity, domains, and conformance discoverable. Evaluation and authority also appear in introductions.

    The loop owns optional base notation; meta-evolution adds the procedure candidate. Link those definitions after concrete examples. They are teaching notation, not new API types or a prerequisite for the quickstart. Diagrams label mutable candidates, fixed controls, and optional feedback. Keep overviews compact; show branching, rejection, and seed evaluation in detailed traces. Use text as well as color and preserve offline readability. Selection may retain the seed; it promises neither a gain nor promotion.

    Open each primary page with a plain-language definition, what the reader supplies, and what they can do with it. Explain declaration fields for values such as Task and Experiment, and public methods for active or inspectable objects such as Session and Run. Keep evaluator measurements distinct from the task's evaluation contract. The programming model owns the core-object progression; link there instead of repeating full contracts. Use an example, then link a runnable guide and its owned reference. Concept pages need no full notebook; supplemental scripts name repository setup. Distinguish evaluator and proposer authorship from permission to read evidence. Keep simulated proposals and measured behavior explicit, and use only verified example results.

    Use recognizable navigation names and links by purpose. Preserve URLs and heading fragments when retitling; navigation supplies the reading order.

    Lesson conventions¶

    Make rewritten instructional pages self-contained: purpose, prerequisites, setup, code, expected observations, explanation, and one focused exercise. Links offer optional depth, not missing steps. A discovery page helps readers choose a tutorial; it need not reproduce every tutorial.

    The limits guide established the pattern used by evaluation, search, feedback, inspection, and persistence: open with the problem and a short task chooser, then put complete prerequisites in one collapsed section labeled Required setup for a fresh notebook, before the executable task cells. Tell readers to expand and run setup first, then run the examples in order. Folding required setup does not make it optional. Keep the actual change, output, interpretation, and exercise visible. Explain each API before use and link to Start here for the full parser explanation. Reuse canonical snippets; all definitions must be copyable from the page. Use inline settings in the chooser instead of duplicate executable previews. Fold shared preparation, keeping the guide's new concept visible: evaluation teaches the grading function; feedback teaches evidence and its use; inspection prepares a mixed history before querying it. Persistence keeps saving, the kernel restart, reopening, and export visible. Its reopening cell is self-contained. Include a focused answer to a likely question and explain what to replace for the reader's own task. Update the newcomer and regression handoff with changed cells, setup discovery, question retrieval, and transfer tasks. Agent preflight does not establish independent human understanding. Test each rewritten guide in a fresh namespace and from outside the checkout with the installed package; executing a prerequisite page first is insufficient.

    The evaluation guide consolidates the earlier metrics lesson. The limits guide consolidates the earlier threshold and budget lessons. Their previous URLs and fragments redirect to the relevant sections. One SDK notebook guide owns setup and real request wiring. Its accounting and tool details are in Reference; larger SDK applications are in Examples. The old migration URL redirects to the retained removal history. CLI, browser, and extension contracts are in Reference. The SDK introduction keeps installation, credentials, request controls, both callables, declaration, execution, and inspection visible. Only the complete request-accounting wrapper is folded as required setup before use. Keep the request cell separate, explain its bound and rerun behavior, and link deeper failure/accounting details from the point where the reader needs them. Feedback, inspection, and saving also run in fresh notebooks. The saving guide additionally verifies reopening after the original Python process exits, with no proposer or evaluator definitions and no exported source file required. The SDK notebook is tested through the official SDK with simulated HTTP responses, including failed requests and missing usage. Those checks establish the wiring and accounting, not live model performance. The harness guide uses a handwritten help assistant to teach both configuration changes, independent answer checks, fresh held-out evaluation, and export/reload. Tests execute its displayed cells and exercise failures and incompatible grading. The policy guide runs inner number searches to grade candidate search settings. Its notebook retains and reopens every inner history, separates inner and outer work counts, compares fresh held-out runs, and tests the fixed budget ceiling. The artifact-domain guide defines a recipe value and codec in visible cells. It separates structural validity from useful steps, rejects foreign proposals, and reopens saved recipes in a fresh process with only the type and codec. The displayed codec also passes the published conformance suite.

    Extract focused code from canonical scripts, keeping required cells in execution order and definitions before use. Start here keeps installation and Python cells visible without CLI drivers or companion lesson imports; its folds contain optional explanations. Tests execute required folded cells, preserve indentation, and match rendered copyable code. Preserve historical fragments; setup links land at the visible fold so readers can expand it. Continuations name their prerequisite page and define each addition. Put verified output beside the command, preferably as comments; longer transcripts can use adjacent output blocks. Explain what changed and why, including failed attempts. Prefer readable fields and response evidence to raw object dumps.

    Use consistent roles: artifact/seed, proposer, evaluator, task and objectives, search, experiment, session, run, explicit feedback/experience, and external controls. Introduce only the roles the current question needs. Selection never grants deployment authority. A failed measurement has no score; a measured wrong response may have a low score. Persistence does not imply resumability, and recorded replay does not rerun a model.

    Evidence and compatibility¶

    Use only Shipped, Experimental/live-only, and Design—not shipped as status labels. Describe deterministic fixtures, dry runs, and retained live captures separately as evidence modes. Shipped lessons need no repeated banner. Never replace missing live evidence with a transcript that looks like a model run. Label illustrative output explicitly; exercises predict qualitative behavior, not guaranteed live scores. Live claims must match retained authorized evidence.

    Example pages name editable content, independent grading, selection data, separate final checks when present, replacement points, and evidence limitations. Notebook mirrors remain byte-identical to their canonical sources. Site builds publish saved outputs without executing notebooks. Keep unique historical measurements and research decisions even when beginner prose is superseded.

    Destination coverage¶

    Each maintained page should answer a distinct reader question. Extend an existing page when the explanation belongs there. Keep unique measurements and design decisions accessible through Development; a historical inventory entry does not require a page in the learning path.

    Add a guide: write the task, setup, runnable cells, expected observations, and adaptation advice. Link it from the appropriate index or navigation and add relevant execution/output checks. No history or redirect entry is required.

    Edit a guide: run its affected executable checks and the rendered-link checks. Tests protect results, complete copyable setup, actual destinations, and evidence. They do not prescribe sentences, cell counts, or submenu layouts. Review explanations and claims against the canonical contracts; use the newcomer walkthrough to assess understanding, answer-finding, and adaptation.

    Move or retire a page: inspect repository links, known published routes, and the fixed tests/fixtures/documentation_routes.json compatibility baseline. Preserve supported anchors with explicit IDs or add a source, destination, and explicit fragment mappings to docs/redirects.json. Remove the obsolete source file; the existing MkDocs hook generates its route, working fallback links, and search exclusion. To move only old fragments from a maintained page, omit target and supply fragments; known bookmarks redirect in the browser while ordinary visits and unknown fragments retain the page. Point current internal links directly to maintained pages. Missing destinations, collisions, and redirect chains fail the build; rendered checks catch broken links and fragments. Keep unknown existing promises until there is evidence for a deliberate retirement, recorded with its reason and replacement in the review. Repository privacy does not establish lack of use.

    The compatibility fixture is a fixed set of promises, not a current page or heading inventory. Add entries only for deliberate compatibility commitments. The pre-#299 migration inventory is retained in history; no hook or test consumes it. The maintenance review records which checks moved, what was removed, and the retained hook responsibilities. #300's contributor instructions should link here rather than duplicate these rules.

    Entrance build and checks¶

    Notebook tests execute displayed cells, verify output, and reopen persisted history in a fresh process. Source-package ZIPs contain installable source and metadata; lesson ZIPs contain runtime files without test clients or repository imports. Missing files fail the build. Download checks execute extracted files outside the checkout and reopen saved results in a fresh process.

    uv sync --locked --group docs
uv run --locked --group docs mkdocs build --strict

    Run the affected lesson and example checks whenever code or captured output changes. The Docs workflow owns the integrated test selection and fresh-install notebook, SDK and download checks. Inspect navigation, code, and output on desktop and mobile. Automated execution and agent visual inspection do not establish human usability.

    Handwritten pages normally stay below 300 lines and notebook cells below 40. The retained live parser and routing guides are exceptions: each keeps an existing complete SDK execution, accounting, and persistence protocol together, with expandable full source. These guides preserve the earlier live walkthroughs; the first-run notebook path stays small and uses the shipped callable API.
