    Trusted-worker administration: plan for #203¶

    Status: Shipped. This page preserves the September 21, 2026 planning snapshot for the implemented M11.4 trusted-worker administration slice, and states below what was built where that differs from the plan. The broader M11 milestone remains Design—not shipped.

    Prepared September 21, 2026 for #203, the fourth M11 slice, after M11.3 merged. This page is the record a reader resolves the decision labels AD1–AD7 and PD1–PD8 against: source docstrings across the slice cite them by name rather than restating the argument. PD6 and PD7 share their labels with M11.3's farewell and one-live-process-per-id rules, which host.py, admission.py and worker_identity.py cite too, so source names these as "the worker-administration plan's PD6".

    The verification record identifies the commits, the checks run and the mutations that did not redden a law. The roadmap owns scope and acceptance; the programming model owns the public API; architecture owns invariants; and the implementation plan owns technical boundaries. The M11 design supplies the subordinate admission, lease and reattachment rules, and is the page a normative sentence belongs in. The command-line guide owns how an operator uses the result; storage and recovery owns the schema step.

    Goal¶

    An operator decides which external workers a store trusts, what each declares it can do, and can withdraw that trust while a run is live — with every refusal landing before a lease, and a withdrawn worker's live lease dying at the broker's next transaction.

    Scope¶

    • The store: schema 5, one new validated table trusted_workers, the v4 → v5 rung, and read-only opening of schema-4 stores.
    • Domain, port, adapters: the trusted-worker record, the trusted-worker port with its SQLite and in-memory adapters, and the generation check plus the revocation sweep inside both work brokers.
    • Admission: the trust lookup and capability match in the host handshake, the registration's generation, and a per-connection guard on an unexpected raise over unauthenticated bytes.
    • Dispatch: what the dispatcher and the loop do when a worker turns out to be revoked — at a claim, and at a stale answer.
    • Operator surface: the meta-evolve workers verb, Storage.trusted_workers(), and the environment row on resume.
    • Record and docs: the design record's new section and fixes, the command-line and durability guides, status wording, this page, and a verification receipt.

    Non-goals¶

    • Multi-host transport and TLS, autoscaling, priorities, preemption.
    • Per-kind routing — a worker serving only evaluations — and multi-call worker processes, meaning capacity above one. Both are recorded as deferred rather than built.
    • Worker respawn. "Replacing a dead worker is administration" stays true and stays unbuilt.
    • A structured, dimension-wise environment fingerprint.
    • The concurrent renewal-versus-expiry and over-capacity race tests, which belong to #204's harness.

    Settled decisions¶

    AD1 The registry is a validated table in the store; schema 5; v4 stays readable¶

    The store schema version moves 4 → 5, with a rung that creates trusted_workers. A read-only open accepts a v4 store by validating it against the v4 shape, and its registry reads as empty. A validated table behind a version bump was chosen over schema_meta rows or an unvalidated side table so that an older binary REFUSES a v5 store rather than silently ignoring its revocations. Installation-level means per store: the table carries no run_id.

    An already-open older process cannot keep writing. The version check runs only at open, so a dispatcher started before an in-place upgrade would hold the v4 store, with the old code in memory, while the new command line migrates it and revokes a worker. Schema 5 therefore carries a BEFORE UPDATE and a BEFORE INSERT trigger on work_items whose body calls a no-op SQL function registered on every writable connection before any schema work. SQLite resolves a trigger body when a statement is prepared, so a connection that never registered the function cannot write that table once the migration commits; its reads still answer. Every lease-bearing write touches work_items, so the old dispatcher's next broker transaction fails whole as a typed durable-store error and the run resumes on the new build. An exclusive-access migration was rejected: leaving WAL fails while any other connection is open, it leaves a check-then-migrate window, and it would refuse the upgrade for a harmless read-only browser.

    One creator, two callers. A fresh store runs no rung — it is built from the current definitions and stamped — so the trigger DDL is defined once and executed both from the rung and from the current-definitions pass that every writable open runs. Both triggers are validated by the exact definition text SQLite's catalog records for them. For a stamped store that validation runs before the definitions pass, so a stamped v5 store missing a trigger is corruption rather than something an open quietly repairs.

    The read side is its own port. A reader offers get and all; the authority adds trust and revoke. Every store hands out the reader, and only the writable one also answers for the authority, so mutation is structurally absent from what anything that merely reads the allow-list holds — including a dispatcher's, where the connection underneath could write — rather than refused at call time. Listing opens a store read-only, so it never migrates one and works while a dispatcher holds it.

    AD2 Operator allow-list; revoke bumps the generation and marks the row¶

    An operator-supplied id needs a TRUSTED row to be admitted or to hold a lease. A revoke is generation + 1 together with status revoked, so a revoked worker's reconnect loop meets an authenticated terminal refusal instead of being re-issued the new generation. Re-trusting keeps the bumped generation. Rows are never deleted: the generation is monotonic for the life of the store.

    AD3 Dispatcher-minted ids need no row¶

    Ids in the reserved worker- namespace are the dispatcher's own: generation 1, and not revocable — to stop them, stop the dispatcher. The dispatcher therefore never writes the registry, the record's "operator authority only" stays literally true, and ordinary runs add no rows. An operator row under the reserved prefix is refused.

    AD4 Capabilities match at admission, against the run as a whole¶

    The row carries the worker's operator-declared capabilities: an opaque string-keyed mapping, shaped like a component's work requirements. At admission the host refuses — authenticated, terminal, before any lease — a worker whose capabilities do not satisfy the union of the run's component requirements, key by key. Every admitted worker can then run every item, which is already the invariant M11.3 relies on. There is no capacity column: the record rejects a worker capacity field whose only legal value is one.

    AD5 No new stale reason¶

    A lease whose generation is not its worker's current one — or whose worker's row is revoked or absent — is STALE_GENERATION, already in the closed set and already crossing the wire.

    AD6 Resume never refuses for environment drift; it reports it¶

    The recorded fingerprint is one digest over five inputs, so no dimension-wise policy is expressible, and strict equality would refuse every resume after a dependency sync. The property that matters — every worker in one drive runs the dispatcher's build — is enforced at each admission instead. Resume computes recorded against current and says the environment changed since start.

    AD7 An unexpected raise refuses the connection, not the run¶

    The host handshake refuses the connection, not the run, for any non-escaping exception raised on unauthenticated bytes.

    Added 2026-09-25, after review: the host keeps the exception on the Refused it returns, and a spawned run chains it, since the wire names only the type. The trust read types every sqlite3 failure, so a damaged store escapes this guard and stops the run. A worker_nonce must match the workers' 64-character hexadecimal format, because Terms echoes it and is sized at that format. The listener keeps only its latest 16 refusals, bounding retained exceptions and the input buffers held by their tracebacks.

    Decisions on the shape of the work¶

    PD1 acquire raises, never returns a second kind of None¶

    The dispatcher's claim step continues on None, so a None-style refusal would spin the drive. It raises a typed run error instead, which is not a root export and does not escape normalization. The epoch fence still refuses first.

    PD2 The generation check sits between the epoch and the row¶

    The staleness rule's order is: the terminal exemption, unchanged; the epoch; then the presented generation against the one the store honours; then the row, the credential and the deadline. Before the row, because a revoked lease loses its row and a row-first order would report "not leased" or "expired" for a worker an operator had revoked. The honoured generation is keyword-only with no default: a default would be a silent "no authority" fallback. The comparison is written in the staleness module, and domain/work.py gains nothing.

    PD3 The sweep frees revoked leases and authors the cause¶

    The expiry sweep in both adapters returns a LEASED row whose generation is no longer honoured to READY at the next broker write, clears the verifier as rollover does, and writes the revocation cause under the existing first-writer-per-attempt rule. A revoked credential then authorises nothing, and the cause survives a dead dispatcher: rollover, a restarted drive's first write, runs the same revocation arm before it frees the other prior-epoch leases (added 2026-09-25, after review found rollover freed such a row with no cause). The cause constant lives in the domain, because adapters cannot import application code.

    A revoke is installation-wide. The registry has one row per worker for the whole store, so revoking a worker frees every live lease it holds in every run in that store, each with a spent attempt and the revocation cause.

    PD4 trust may widen a trusted worker's capabilities; narrowing or changing one is refused¶

    On an already-trusted id, trust with the same capabilities is a no-op, and with a superset — every existing key kept at a canonically equal value, new keys added — it updates the row at the same generation: a larger set cannot invalidate an admission that already matched, so declaring one more capability costs no lease. Dropping a key or changing a value is refused, because an admission that matched may depend on it. On a revoked row, trust sets it TRUSTED at the kept, bumped generation and replaces the capability map wholesale — that is the only path by which a map is narrowed, and it is what "revoke it first" means. The superset rule is keyed on the row's status, never on the row's presence: rows are never deleted, so a presence rule would make narrowing impossible. A second revoke does not bump twice, and revoking an id nobody enrolled is refused, because a typo must not report "revoked".

    PD5 The host gets a lookup, never the port¶

    A host admission carries a lookup that reads through a reader's get and nothing else, in a field named lookup, never trust. The evidence:

    1. The store hands out a reader: test_the_allow_list_a_store_hands_out_is_a_reader_whatever_it_may_do, on durable and read-only stores.
    2. A drive supplies a reader factory. The listening host calls it when opening, before creating a key or listener; a spawned backend leaves it unused. It never asks for trusted_worker_authority (test_trust_lookup_handoff.py).
    3. mypy types trusted_workers() as TrustedWorkerReader, which has no trust or revoke. Types cannot tell a reader's get from a writer's, since TrustLookup is a bare Callable, so the handed lookup's provenance rests on (2).

    2026-09-25: acceptance evidence reworded from a directory AST ban to the laws above; the rule is unchanged.

    A host is spawn-policy or operator-policy by construction: the admission refuses minted ids together with a lookup, and refuses neither, so "no lookup, so everyone is admitted" cannot be built. A spawn-policy admission carries no lookup at all and answers generation 1 without consulting one.

    PD6 Conflicting requirements are not an eighth start refusal¶

    Two components declaring one key at different values is valid inline and with spawned workers: neither matches work requirements against a worker. That field's only reader compares it for equality — host against worker at a handshake, recorded against supplied on every resume — and both stay byte-identical. It is unsatisfiable only under every-worker-runs-everything, so the listening host refuses it when it opens, before the rollover. Both seven-row start-refusal tables stay untouched.

    PD7 Equality is type-strict¶

    Capability values are compared as canonical payload bytes. Python equality would let 1 satisfy True, and existing tests already declare boolean capabilities.

    PD8 Drift rides Run, not RunSummary¶

    A run summary promises capabilities without verifying compatibility to resume, and feeds the inspect, compare and browser goldens. Drift is therefore a method on Run, and the command line prints it as one extra row only when there is drift, so every existing resume output stays byte-identical.

    Two pull requests¶

    Both planning passes found the same thing: operator-named ids already take real leases, so broker enforcement without the door would abort a listening drive, and the door without broker enforcement would make revoke a lie. They land together.

    The first: registry and revocation¶

    An operator can enrol and revoke, and it is enforced at the door, in every broker transaction, and in the dispatch loop. What it built, where that differs from the plan above:

    • The schema-5 DDL, the v4 → v5 rung and the write guard live in one new module, adapters/sqlite/schema_v5.py, rather than growing schema.py. The read-only shape map holds exactly the versions it has a shape for, 4 and 5.
    • The table's key is worker_id TEXT PRIMARY KEY NOT NULL: in SQLite a TEXT primary key does not imply NOT NULL.
    • A store answers through two capability Protocols, not one. Storage.trusted_workers() returns a reader — a distinct object with no trust and no revoke, on every kind of store, including a writable durable one — and Storage.trusted_worker_authority() returns the writable port and is declared by the durable strategy alone. One method name would have answered True for a read-only store under a structural check, so the writable half is a name a read-only store does not have; and the reader is a separate object rather than the port under a narrower type, because a host is handed one bound get (PD5) and a get bound to the port would carry revoke on its __self__. The writable store's reader reads the live table over the store's own connection, so a revoke made through the authority, or by an operator's command on another connection, is visible at its next get.
    • Placement. decide_trust and decide_revocation live in ports/worker_registry.py beside the Protocols, so the two adapters cannot drift on a rule. The store capabilities are Protocols of their own there, not a method on WorkTransactor, whose capability is its one method: a strategy with a broker and no registry would stop satisfying it. The workers verb is the top-level worker_administration.py, not part of cli.py (at its length ceiling) or of distributed/, since the operator writes the allow-list and the dispatcher and the transport only read it. The diagnosis rule moved into each adapter's work_diagnosis.py to keep the lease and ledger modules under the length guideline.
    • The door's generation read raises the handshake's own refusal rather than returning a sentinel, because there is no number that means "no". It is read at the Hello before the build comparison, and again just before the reservation.
    • The SQLite generation read lives once, in the submission classifier that renewal, status and acceptance already share, rather than being copied to three callers whose whole job is to agree. The in-memory ledger is handed the answer by the broker that holds the registry.
    • The diagnosis precondition split in two: whether the attempt is still undiagnosed, and whether the caller's credential authorises a diagnosis. The sweep asks only the first — a stored lease carries a digest, not the secret — and the in-memory ledger's held lease does carry the secret, so one shared rule would have passed there and refused in SQLite.
    • The sweep clearing the verifier has no law of its own. Planting "keep the verifier" leaves every law green, because the cause write already refuses a later diagnosis and every other path meets the generation check first. It is kept because the record requires it and because it is one statement shared with release and rollover.
    • Answering a revoked holder also RELEASES the item it was holding. Settler._answer sends the answer; then, when holds_a_revoked_credential says it names the connection's own credential, it calls fail_attempt (even when the send failed) and raises the TransportFailure that closes the connection. The answer is best effort: a close can drop what the socket had not taken, and the door's refusal tells the worker anyway. That broker write's opening sweep is what frees the row and records WorkerRevoked, so the cause fail_attempt passes goes unused. The answer is classified by a read, which by contract moves nothing, and the binding that would have carried the lease into the loop's own release is dropped before the outcome is settled — so without that release the row stays LEASED with nothing bound to it, which the dispatcher refuses by name rather than waiting out. PD3 is still where the freeing happens; the refusal is what makes a write happen at all on that path. A refusal from that release is not swallowed: DispatcherSuperseded and DurableStoreError are facts about the run, they outrank failing one connection, and they end the drive.
    • A workers list or workers revoke pointed at a path holding no store exits 1, the existing mapping for a refusal from the library, not 2. workers add CREATES the store and exits 0, because an operator enrols the workers a run will use before that run exists. Exit 2 is reserved for a malformed or reserved id, which a parser type refuses in the domain's own words before any store is opened.
    • An unreadable trust row stops every run its worker holds a lease in. A trusted_workers row the decode refuses is DurableCorruption — never skipped, because skipped as absent it would free a lease nobody revoked, and skipped as trusted it would honour an authority nothing can read. The revocation sweep that opens a run's broker writes reads the row of each worker holding one of that run's leases, so while the damaged worker holds a lease in a run, every write in that run stops until the row is repaired, whoever asks. So does anything that looks that worker up by name: its own claims, workers list, and the door, which stops any listening run the worker connects to. A run it neither holds a lease in nor connects to never reads the row and keeps writing, since the sweep is scoped to its run. Kept, lawed and documented rather than softened: a lease's authority is not something a store may read past.

    The second: capabilities and the record¶

    An operator can declare what a worker can do and have it matched at admission; a resume in a changed environment is reported; and the design record carries its own worker-administration section. What it built, where that differs from the plan above:

    • The unexpected-raise guard is the last arm of the host handshake's advance: a raise the handshake did not expect on bytes a peer chose refuses that one connection, unauthenticated, naming the exception type and never its message, while anything a run must stop for still stops it.
    • The matcher is worker_capabilities.py, a top-level module (about 110 lines, not the estimated 75) beside the workers verb that writes declarations, not in manifests.py, which answers whether the code is the same and is at its length budget. It holds the union of a run's requirements, and the first key in sorted order a declaration misses or declares at a different value. Its admission and command-line laws live in tests/test_worker_capability_admission.py and tests/test_cli_worker_capabilities.py rather than in the matcher's own module, which holds the pure-function table.
    • The door matches capabilities inside the same call that answers the generation, so trust and capabilities always come from one registry read, at both reads. The listening host computes the run's requirements once when it opens, before the key file and the port, so a run with conflicting requirements writes neither.
    • Writing commands report their transaction's resulting row, including the generation and the full declaration for add. They do not infer whether the command changed anything from a separate read, which could race another operator. worker_administration.py passed 300 lines when --capability arrived; the review round's trim brought it back under.
    • The plan's "skip the shared freeze" mutation stays GREEN: a declared value is also frozen by the SQLite encoding and compared by canonical bytes, so any one of the three is masked by the other two. The command-line array law goes red instead under "the command line takes arrays and objects as literal text".
    • The drift row is printed after the drive, so a resume that raises shows only its error. Stale M11.2 text calling the fingerprint "recorded, never compared" was also rewritten in domain/components.py, beyond the two files the plan named.
    • The identity evidence is tests/test_workers_mint_no_identity.py. Three of its mutations go red through the replay fold's own refusal rather than the law's assertion — a second guard in the domain, recorded rather than hidden.

    Laws¶

    Each law goes red under a named mutation, and where a law could pass for a weaker reason the neighbouring case that rules it out is named with it.

    • Registry, against both adapters with a completeness guard: insertion at generation 1; an identical trust is a no-op, a superset widens at the same generation, and a narrowed or changed value is refused — a triple, because an always-overwrite registry passes the first two alone. A read-only store's reader has no trust or revoke attribute, is empty below schema 5 and table-backed at 5. A revoke bumps by exactly one and marks the row, read back through get rather than from the return value; a second revoke does not bump; an unknown id is refused with no tombstone; re-trust keeps the bumped generation and the status is asserted; rows never vanish; the reserved prefix is refused using an id the grammar accepts, or the grammar would refuse it for the wrong reason. SQLite also: survives a reopen, sees a second connection's revoke, leaves the row unchanged when the commit tears, and reports a damaged row as corruption.
    • Broker, one contract tuple over both adapters: an absent, revoked or wrong-generation operator id is refused with rows equal before and after, and a reserved worker then claims that same row, so the queue was not merely empty; a reserved id needs no row and the registry is still empty afterwards; a superseded epoch is answered first; after a revoke through the authority, renewal, submission status, acceptance and release all refuse with the stale generation while the deadline is still ahead; the swept row is READY with the revocation cause and its attempt still spent; the terminal exemption still answers duplicate; revoking one worker leaves another's lease live; and one revoke frees that worker's lease in each run in a two-run store, at that run's own next write. Plus a differential sequence across both adapters, a torn sweep, and the precedence cases.
    • Wire: three enrolled ids revoked through the real port exhaust an item, which ends as an infrastructure failure naming the revocation at the last attempt; a re-enrolled worker resending a lease from before its revoke is answered and stays connected; an idle revoked worker is failed at its next claim with attempts unchanged.
    • Admission: unenrolled and revoked are refused authenticated and terminally, before the run's terms cross; a revoke landing between the Hello and the manifests is caught by the second read; a host with a minted policy and a lookup, or with neither, cannot be constructed; a spawn-policy handshake admits its minted id at generation 1 against an empty registry.
    • Real processes, because command-line code has escaped a green suite in this repository by never being launched: every exit code of the verb, through a real process as well as through main(argv). A worker nobody enrolled exits 2 saying it is not enrolled, while the run's rows stay NON-EMPTY, ready, unspent and on the same epoch and the port stays open — the emptiness matters, because an all(...) over an empty work table is true — and then, enrolled through the real verb, the same run finishes. A revoke delivered as a real command while a worker is inside its call sends that worker back to the door, where it exits 2 saying it was revoked, while the item it held completes on another worker under the same trial with two attempts and the revocation recorded against the first. Each worker waits on a release marker of its own: one shared marker lets the run reach its stop and close the port before the revoked worker is back at the door, after which it would back off forever. A worker declaring the wrong capability exits 2 naming the key and both values, at no cost to the run.
    • Schema: each frozen capture opens writable and lands at 5 with an empty table and unchanged events; a read-only open of a v4 store leaves it untouched; a v5 store without the table is corruption. A raw connection opened on a v4 copy before the migration — standing in for the older process — is refused on update and on insert into work_items once another connection has migrated the store, and can still read. The trigger lifecycle has one law per caller: a freshly created store holds both exact definitions, a migrated one holds both, and a stamped store with a trigger dropped by hand is corruption.
    • Capability matching: declared equal to required is admitted; a superset is admitted; a missing key is refused naming the key; a differing value is refused naming both values; 1 does not satisfy a required True; nested maps, arrays and nulls compare; empty requirements admit anything, which is the control; and two components requiring one key at different values is refused when the listening host opens, with rows ready, attempts unspent and the epoch unchanged.

    Acceptance¶

    • Every runtime refusal the record's admission table names has a law asserting the refusal leaves rows ready, attempts unchanged and the epoch unchanged. Unenrolled, revoked and capability mismatch are also shown with real processes. The two structural rows cite the laws that already close them: the codec by the start and resume refusals, capacity by the handshake pin and the broker's capacity inequality.
    • After a revoke through the registry — never by editing a lease — renewal, submission status, release and acceptance all refuse with the stale generation in both adapters, and the process law shows the item completing on another worker under the same trial with two attempts.
    • An item exhausted by revocations ends as an infrastructure failure whose exception type is the revocation cause, and nothing new enters the closed wire error map.
    • An older process that held the store open across the migration cannot write work_items afterwards, and a read-only store exposes no trust or revoke.
    • The frozen schema-4 captures stay byte-identical and open read-only; inline and spawned-worker runs stay byte-identical in events and work rows, with the registry empty; and a host is handed a lookup that reads only through a reader, by PD5's three pieces of evidence.
    • Existing listening-mode tests pass after enrolling their ids, with no assertion weakened.
