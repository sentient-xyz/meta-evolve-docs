    Verify and publish the author API release: plan for #319¶

    Status: Design—not shipped.

    Prepared September 18, 2026 for #319, under #313. This plans the coordinated 0.2.0 package release. It does not publish a package, create a tag, change package metadata, deploy documentation, or certify the broader MVP.

    The roadmap owns the acceptance gate; the foundation and comparison decisions own the selected API. The release checks below own the concrete verification matrix. Use the current programming model and architecture for shipped meaning.

    0. Set the release scope and publication ownership¶

    Recommended scope: a focused 0.2.0 author API release, with the full MVP tracked separately. This scope choice is awaiting Salah's response at plan preparation. It is not inferred from the pre-1.0 compatibility reset.

    There is a real overlap with existing release work:

    Owner Relationship to #319
    #268 — MVP scope Requires completion of M11 concurrency, live-workflow evidence, environment claims, and independent acceptance beyond this API revision. Remains open.
    #272 — Distribution verification Owns wheel/sdist installation, browser assets, matrix CI, and a repeatable publishing procedure. Implement/reuse this seam rather than create a competing packaging system.
    #276 — Publication Names Salah as final acceptance/publication owner, Quancore as procedure owner, and Bhasker as independent post-publication verifier. Retain these responsibilities unless explicitly revised.

    Before upload, record whether this is the narrow API cut or the full MVP and which existing acceptance requirements apply. If the narrow cut is selected, record that scope explicitly in the release-owner handoff; leave incomplete MVP issues open and make no concurrency/live-quality claim. If the full MVP is selected, #319 can prepare the distributions and verification but publication waits for that release's remaining gates. Do not silently waive them.

    Confirm the exact PyPI project/version, publication account, and supported environment matrix with the existing release owner. GitHub administrator access was verified for both repositories; it does not establish PyPI ownership. Use the proposed matrix in the checks page as a concrete starting point.

    1. Add the missing distribution and publication seam¶

    Only ci.yml and docs.yml currently exist. Runtime CI tests the checkout; Docs CI verifies an installed source ZIP. Neither builds, validates, and tests both release distributions or uploads to PyPI. No existing release workflow or standalone publishing procedure was found in the source checkout.

    Extend the existing CI packaging responsibility with a small, deterministic installed-package smoke entry point. It must work against an interpreter and artifact supplied by the caller, outside the checkout. Reuse examples and history checks; do not invent another acceptance framework.

    Use one reviewed publication workflow or the existing owner's equivalent repeatable procedure. Keep build/verification separate from the upload step. The upload consumes the exact artifacts already checked, with the same hashes; it must not rebuild a different wheel or follow a moving branch.

    For GitHub Actions, prefer a protected publication environment and PyPI Trusted Publishing, with OIDC permission confined to the upload job. This avoids a long-lived package token in the repository. Pin reviewed action/tool versions when implementing. See PyPI's publishing instructions.

    If this is the first PyPI upload, configure and verify the appropriate pending publisher for the actual repository, workflow, environment, and account. A pending publisher does not reserve a project name; recheck before upload. See creating a project through Trusted Publishing. If access is missing, finish build/checks and the concrete handoff; identify the account/configuration action needed instead of improvising another index.

    TestPyPI is optional for rehearsing the upload mechanism. It neither satisfies public-PyPI verification nor establishes ownership of the production name. Publishing remains an explicit later release action, never a side effect of ordinary PR tests or a docs build.

    2. Prepare and freeze one release candidate¶

    Use a focused release-preparation PR after the packaging seam is usable:

    1. Set pyproject.toml to the selected release version and update its own distribution entry in uv.lock. Review any unrelated dependency movement.
    2. Validate metadata, Python requirements, license, README rendering and links, CLI entry point, extras, and source/docs/issue URLs. Add missing public project URLs where needed; keep unrelated packaging cleanup out of scope.
    3. Replace current-install guidance that says the package still reports 0.1.0 in the migration/status pages. Preserve 0.1.0 inside historical captures, source patches, and dated evidence. Do not globally replace version strings.
    4. Prepare release notes from the existing migration guide: five changes, retained forms, externally owned authority, supported environments, and read-versus-resume limitations. Existing deterministic examples do not become live-model evidence in the announcement.
    5. Merge/reconcile the preparation and identify a clean, immutable commit R. Record the exact lock and source tree. Build all final artifacts from R.

    R is a plan symbol, not a literal git ref. A source/version/docs change after freezing it creates a new candidate and invalidates affected evidence. A later verification-record commit can describe R; it must not silently move the tag or be substituted for the tested source in publication.

    3. Build and verify the distributions¶

    Build the wheel and source distribution through the declared Hatchling backend using a recorded toolchain. Record the resolved build backend as well as uv, Python, and runtime/test dependencies: the current unbounded hatchling build-system requirement is not pinned merely because uv.lock is recorded. Use a scoped build constraint if needed for reproducibility.

    Validate both archives' metadata and included package resources. Install the wheel and sdist separately into clean environments, forcing the source path for the latter. Rebuild from the unpacked sdist outside git to prove it contains what its backend needs. Verify the package origin and installed source files, not only the reported version. Wheel/sdist compression need not be byte-identical to one another; their installed code and intended resources must agree.

    Build the documentation source ZIP from R too. It is a third distribution route and must match the same package source/metadata, but its hash and archive layout are distinct. Preserve the deterministic ZIP test already owned by docs/hooks/entrance.py and test_lesson_downloads.py.

    The checks page specifies fresh-install smoke cases, historical compatibility, supported profiles, and evidence fields. Run the maintained full runtime and Docs workflows on R; baseline passes on 1607afbb… cannot substitute. Reuse one successful result per exact revision and required environment rather than rerunning identical suites without cause.

    4. Assemble the release handoff before publication¶

    Produce one reviewable packet containing:

    • Commit R, version, proposed tag, final wheel/sdist/source-ZIP hashes, build-tool versions, source manifest, and exact installed-package receipts.
    • Hosted runtime, packaging-matrix, and Docs run links for R, with actual pass/fail/skip counts, reasons, supported environments, and residual limits.
    • Historical read/resume outcomes and explicit negative invocation/environment checks. Retain evidence that refusal performed no component work or new facts.
    • Release notes, rendered candidate docs, immutable documentation archive, public-index/project configuration, and the exact upload/deployment procedure.
    • The chosen narrow/full release scope and the existing owner's final claims and publication decision, plus the independent verification handoff.

    Keep durable evidence beyond the existing 14-day Docs artifact retention. Attach receipts/checksums and necessary logs to the release or a maintained evidence record. Temporary /private/tmp paths alone are not release evidence that another contributor can retrieve.

    The existing #276 explicitly says “Salah retains final acceptance and publication authority.” Prepare the complete packet first; request any still missing publication decision against these concrete artifacts. If Salah has already authorized the exact publication in the implementation session, retain that authorization rather than asking again. Planning #319 alone is not upload authorization.

    5. Publish the exact artifacts and matching documentation¶

    After the applicable acceptance and publication decision:

    1. Recheck tag/version/name availability and that R and artifact hashes match the approved packet. Create the version tag at R and prepare a GitHub release with the reviewed notes and assets using the selected procedure.
    2. Upload the verified wheel and sdist; record the actual index response and compare the index's file hashes. Do not rebuild between verification/upload.
    3. From a clean environment and outside the checkout, install the exact version from the public index, including a source-install check. Verify public asset hashes, metadata, imports, quickstart, CLI, saved history, and browser extra.
    4. Publish the reviewed GitHub release with its verified assets and notes. Keep staged release/docs material separate until the index check succeeds.
    5. Build/deploy docs from R, or use the verified R artifact. Update meta-evolve-docs/.source-commit to R; preserve the static repo's hosting files and README. Inspect its actual remote head first: the local sibling checkout observed during planning was stale.
    6. Verify the Pages build, public marker, migration/reference/install routes, and downloaded ZIP hash/metadata/source. Test real public responses, not just the deployment job or local files. Record source and docs commit IDs.

    The current docs deployment is a separate static repository served from its main branch root through GitHub Pages. Reuse that arrangement; a new hosting service or cross-repository deployment framework is unnecessary. A moving homepage cannot retain all version-specific evidence, so keep the tagged source and reviewed docs archive available with the release.

    6. Stop, recover, and close honestly¶

    Failure point Required response
    Before upload: tests, metadata, permissions, or claims incomplete Keep artifacts staged. Fix the owning problem; create a new candidate if source changes. No tag or package claims imply a pass.
    Ambiguous/partial upload Inspect the public index before retrying. Account for each file/hash; do not blindly upload a rebuild or mark the release complete.
    Public install or asset mismatch Stop announcement/docs advancement, retain evidence, and use the approved correction/yank procedure if necessary. A fix requires a new published version; do not replace bytes behind an existing version/tag.
    Package works but docs deployment fails Keep #319 open, report the package/docs split, and redeploy the same reviewed documentation artifact. Do not conceal the successful package upload by calling the whole operation rolled back.
    A later defect affects saved runs Preserve old distributions and history. Reverting a package/docs pointer does not migrate stored facts or make an older runtime safe for newer stores.

    Completion requires both public artifacts and matching docs, recorded fresh installation and compatibility evidence, and the independent verification required by the selected publication process. An automated smoke run cannot be reported as Bhasker's independent acceptance.

    Update #319 and #313 with the evidence and reconcile their stale checklists. Close the API parent only after all selected children and publication gates are complete; leave broader #268/MVP issues open unless their own gates are met.
