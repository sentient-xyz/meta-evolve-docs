    M11 trusted-concurrency design¶

    Status: Design—not shipped.

    This page is the subordinate design record for #10. The milestone roadmap owns status, order, gates, and exclusions. The implementation plan owns technical staging and package boundaries. The distributed direction owns the longer arc through M12. This record owns vocabulary, the consistency model, the durable rules concurrency changes, and the compatibility promises.

    Nothing here makes a name importable or an invariant implemented.

    Longer than the other design records, deliberately: the rules below are one interlocking set — the outstanding-work definition, the decision barrier, the evaluation disposition and the reservation fold are four readings of the same predicate, and splitting them across pages would hide that they must agree.

    What distributed start refuses¶

    The milestone roadmap owns the scope statement. This record owns the refusals that enforce it: seven configurations, each a CapabilityError naming its reason: six checked at start before any claim or lease, and the environment fingerprint, which is checked when a worker is admitted, before it can claim. Single-process resume ships in M11.2: prepare_resume admits a distributed run (session_preparation.py, mode not in ("durable-local", "distributed")) and re-runs admission against the recorded values, with Session.drive() rolling the epoch over as the explicit recovery step. There is no Dispatcher.resume. What stays M11.3's is the CROSS-PROCESS re-read: the "Re-read on resume from" column below describes a worker rejoining a run another process is driving. Admission turns on a declared capability, never a named preset — checking for a specific policy by type would be the policy-specific coordinator branch the constitution forbids.

    Refused Reason
    A declared context policy Pushed context binds a fact to an exact stream position, and its cutoff is strict where pull's is inclusive.
    A declared experience access Pull experience appends audit facts synchronously from inside the proposer, behind stream-global guards.
    A policy without the cohort capability The capability is a declared width and a producer, and only BestOfN declares the width. Greedy chains strictly, so each parent is the previous result and a generation has nothing to draw from. BestOfK is the natural second — _cohort_parent already freezes an incumbent for a whole cohort of k — but it neither declares a width nor produces a generation, which is #201.
    A finite token, wall-time or spend ceiling The shipped presets hand each trial the run's whole measured allowance — bind copies the declared token and wall-time ceilings, and narrow adds the remaining spend at decision time — so a second cohort member, computed from the same base where nothing is yet settled, has nothing left to allocate. Zero is refused with the rest; the budget section owns why.
    A custom codec Codecs carry no manifest; durable-local already refuses them. A worker with the wrong codec is worse than one with none.
    A component not declaring retry_safe Automatic retry of unsafe work is dishonest. Determinism is not required: that is durable-local's rule, for M4's interrupted-equals-uninterrupted guarantee, which a distributed run does not claim.
    An environment fingerprint mismatch See environment fingerprint. Compared when a worker process is ADMITTED, against the dispatcher's current build; a run's recorded fingerprint is not re-checked on resume (#203).

    Every restriction is a refusal, never a silent degradation. Paid concurrency needs conservative per-trial allocation of measured dimensions, which M11.0 opened as #206 and which the measured-ceiling refusal above stands in for until it lands.

    Vocabulary¶

    Four identities, none collapsed. The identity concept already establishes that equal bytes in different causal positions stay different occurrences; a work attempt is a third axis and folds into neither.

    Term Meaning Identity
    Trial The logical experiment. Unchanged. Derived from its decision.
    WorkItem One deliverable unit. At most two per trial: proposal and evaluation. Stable from the trial and the kind.
    WorkAttempt One worker's bounded attempt at a work item. The work item and an ordinal, unique in the work table.
    Worker A trusted execution identity with declared capabilities and capacity. An operator-supplied id plus a monotonic generation.

    Execution terms¶

    What runs work, and how its failures divide. None of these is an identity.

    Term Meaning
    Worker process The operating-system process that hosts one Worker and connects to the dispatcher. It runs one call at a time: capacity is one, fixed by the worker protocol.
    Admission The handshake that authenticates a worker process against the run's shared key and then checks that it runs the same build and resolves the same components. It happens before that worker can claim anything.
    Reattachment A worker reconnecting under its own identity and resending the result nobody acknowledged. It preserves ACCEPTANCES, not work: a lease is rebound only inside the epoch that issued it and only while its old connection is still registered, and any other resend is answered Duplicate or Stale from the store.
    Executor What runs a component on a work item's resolved inputs and returns its result, holding no coordinator, storage, clock or broker.
    Attempt failure Input resolution or the executor raised, outside the escaping set. The attempt is released and the retry bound decides.
    Completion failure A fault after the component returned: building its facts, validating them, or committing them. Its cause is recorded and it propagates; the dispatcher does not run the component again, and once the lease ends the recorded cause decides whether a later drain may.
    Input resolution The store reads that resolve a work item's inputs before its component is called.
    Submission A worker presenting a work attempt's result under the lease that attempt was issued. Never an enqueue.
    Duplicate submission A submission at a completed work item by its accepted attempt, with a token that proves. Answered with the stored acknowledgment.
    Stale submission A submission at a work item this run holds, whose lease no longer authorises it: the item was never leased to it, has ended, was completed by another attempt, or its lease is superseded, fenced or expired. Refused, never a contract violation.
    Stale reason The one precondition a stale submission failed, from a closed set: not leased, ended, superseded attempt, other worker, stale generation, unproven token, prior epoch, expired. Expiry is recognised even after it has been swept, from the token verifier the row keeps, so a lease that ran past its deadline reads expired either way. When several hold, terminal rows are checked first, then the epoch, then the row's lease.
    Submission status What a submission would be answered, read without acting on it: live, duplicate with the stored acknowledgment, or stale with its reason. Advisory; the acceptance inside the committing transaction decides.
    Endpoint One backend as the dispatch loop sees it: the inline helper thread, or one worker connection. Every endpoint speaks the same dispatch messages.
    Transport failure A connection that breaks the protocol, or breaks. Its leases are released with cause WorkerDisconnected, the connection is closed, and the others continue.
    Dispatcher supersession A second dispatcher's rollover of the run's epoch, after which every commit and broker write the first one attempts is refused with DispatcherSuperseded. Exclusion, not failover: nothing decides which dispatcher should win.

    Semantics settled in M11.2¶

    Four questions the vocabulary above left open. Each was answered because two adapters had answered it differently, and the shared contract suite could not see the disagreement.

    An enqueue is the same when the fields ENQUEUE AUTHORS are the same — the trial, the kind and the retry bound. state and attempts belong to the broker, not the enqueuer, so a repeat enqueue of a work item that has since been leased is the same item further along, not a conflicting claim. Comparing them would make a retried commit of an already-partly-progressed cohort fail, which is the opposite of what an idempotent enqueue is for.

    Enqueue is atomic across a generation. A cohort is enqueued as a generation, and a half-enqueued generation is the torn state the same-transaction rule exists to prevent. Every row is validated before any row is written.

    An acknowledgment is opaque. It is bytes the broker records and returns without reading. A structured payload invites two writers to disagree about how to encode it, and two did.

    A state and its justification are ONE fact. LEASED does not exist without the lease that justifies it; COMPLETED does not exist without the accepted attempt, its token and the acknowledgment. A lease also names its run, so a submission addressed to another run is refused rather than answered stale. States whose evidence is optional are how an orphaned row becomes permanently unclaimable in one implementation and silently released in another.

    Attempt identity must be distinct, not secret. Authority comes from an opaque lease token, whose digest alone is stored, and from a monotonic fence. A derived attempt id therefore adds no risk and needs no entropy source. The result key is stable from the work item and is an idempotency key, never a credential.

    The bootstrap trial has only an evaluation work item.

    A dead attempt is released, not waited out. The broker gains release, fenced exactly as renew is and appending no fact: the scheduler already knows the attempt is dead, and letting the deadline expire instead idles the item for a whole lease duration to learn what it was told. The transition an unfinished lease leaves behind is released() / RELEASE_SQL, the same statement expiry and rollover make, so exhaustion goes terminal by the same rule in all three. The terminal LOGICAL fact an exhausted row then owes is the reclaim step's; a ledger edit does not discharge it.

    Three outcomes. A raise that the adapters' own normalization boundary lets escape — the five infrastructure types plus CapabilityError, DispatcherSuperseded and StaleCompletion, published as escapes_normalization — while resolving inputs or inside the executor aborts the run and is never retried; it records no cause. Any other Exception raised while resolving inputs or inside the executor is an attempt failure: released with its cause, and the retry bound decides. Reusing that boundary rather than writing a second taxonomy beside it is the point: retrying an escaping raise would spend the retry bound re-running an impossible preflight. And a fault after the component returned is a completion failure — building the facts, the provisional fold, the keepalive or the commit: the cause is recorded against the lease and the error propagates, because re-running a component that already answered spends a provider call to reproduce a coordinator fault. The row stays leased until expiry or rollover returns it to ready. Whether a later drain then may run the component again is decided by the cause recorded for that attempt, and not by the drain: see the completion-stage split below. Exception, not BaseException, so an operator's interrupt is neither released nor diagnosed.

    record_failure writes a cause and moves no state. It follows the same diagnosis rule release does. The first writer wins per attempt, on every path. While a lease is held, only its holder may write. Once expiry has collected the lease, only the row's latest attempt may still diagnose, and only by proving the token it was issued against last_lease_token_digest, a verifier kept on the row through expiry and cleared when the lease is released or rolled over; a row with none refuses. Terminal rows are never rewritten.

    A committed artifact missing from storage is corruption, not an attempt failure. Proposal parents and the evaluated artifact are ids the fold has already validated as committed, so a store answering "not found" for one raises DurableCorruption and aborts rather than spending the retry bound.

    An inline call is renewed while it runs. The component runs on a daemon helper thread, inside a copy of the caller's context, and every BaseException it raises is handed back to the dispatcher thread; the dispatcher thread renews the lease every lease // 4 broker-seconds until the call returns, because renewal is a write on the store's one connection. Lease duration is per run -- Session.drive(lease_seconds=...), at least 10 seconds, 60 by default -- and one broker instance carries it into both acquire and renew. Each check is one broker call, renew_or_stale, which renews the lease or answers its stale reason in the transaction that refused it, so the reason is never a later reading of the row. A refused renewal raises StaleCompletion carrying that reason at once, without waiting for the component, whose result could no longer be committed. A lease the row records as already accepted, or an item that vanished after this dispatcher claimed it, is DurableCorruption instead. Python cannot cancel a thread, so that call may still be running. Execution is therefore at least once, inline exactly as for a worker process that lost its lease: nothing in the process refuses a later drive or resume of the same run while an abandoned call runs, and that call may run beside the retry. Acceptance stays at most once -- the abandoned call's lease is stale, its epoch superseded by the resume's rollover, and the in-transaction acceptance decides regardless -- and the abandoned call is never settled: every call carries a generation, an abort retires it, and a retired call's outcome is dropped when it arrives. A renewal that fails for any reason while the call runs ends the drive, not the attempt: the component is still running, so the row is left LEASED rather than released for this drive to claim again beside it. The honest bound: renewal happens between two readings of the clock, so a single step longer than the whole lease still loses it.

    One completion path. Every backend is an endpoint in one selectors loop on the dispatcher thread, and every outcome reaches the stream the same way: build, provisional fold, keepalive, commit with the acceptance. The inline endpoint runs one call at a time on its helper thread and hands its outcome back as the same message a worker connection decodes. A worker's result is classified by its submission status first -- a duplicate is answered with the stored acknowledgment and a stale submission with its reason, and neither builds or writes anything -- and a stale or duplicate refusal raised by the acceptance itself is answered the same way. An inline result skips that read, because its lease is the one the dispatcher holds, and a stale inline submission raises where a worker's is answered. The policy is asked only when the work table holds no ready or leased row, and then only if the stream agrees nothing is outstanding: the table empty while the stream still owes work is corruption. A leased row no call of the dispatcher holds is refused by name rather than waited out.

    Liveness under a blocking commit. Commits stay synchronous on the one dispatcher thread, so while one result commits every other connection waits. A bound lease is renewed every lease // 4 while its connection has been heard within lease // 4, heard meaning a heartbeat the loop read, stamped with the dispatcher's clock when it was read. Before every step that can block -- a commit, input resolution, reclaim, a policy call -- the loop drains every readable connection and renews every lease whose deadline is closer than lease // 2 and whose connection was heard within lease // 4, one broker call per lease. This includes the lease whose queued result is about to be built: its freshness check follows the drain, and its final authority check still precedes acceptance. Silence is judged only after draining, past 3 * (lease // 4), so a heartbeat buffered while the loop was blocked counts. A healthy lease can expire only if a single step exceeds lease // 2: a liveness loss, never a safety loss -- the worker is answered stale, the attempt is retried, and at most one completion is accepted. Each step is measured, and one past lease // 4 is recorded as an ephemeral overrun, never written to the stream or the work table.

    The wire. A frame is a four-byte big-endian length and that many bytes of JSON, the durable format's tagged encoding bound to a wider registry that the durable format does not share. A declared length over max_frame_bytes is refused from the header alone. Leases travel whole, secret included, and no refusal quotes the frame it refused. An exception crosses only as a name, message and fields rebuilt from a closed table -- the escaping set and the candidate-encoding fault -- and is never pickled or resolved by name. An undecodable frame or invalid message is a transport failure; a candidate the codec rejects is the same invalid-output failure it is inline, because the worker encodes it with the same function. A write that has not drained within its deadline fails its connection. Multi-host use is documented and untested: it needs TLS.

    Worker processes. With an explicit process backend, a distributed run executes its work in worker processes, spawned by the dispatcher for its own run or started by an operator against a dispatcher that listens. Spawned workers are admitted BEFORE the epoch rolls over, so a handshake that fails leaves a genesis-only run whose epoch is unchanged, with nothing claimed and nothing spent. A listening dispatcher validates its terms and opens before rollover, then admits workers during the drive; a run whose workers have not arrived yet waits rather than failing, while one whose spawned workers have all died is refused by name.

    Admission is five messages over the same frames. Nothing that depends on the run, and no lease secret, crosses before its peer has proved it holds the shared key: each authenticated frame is an opaque body and a MAC over exactly the bytes sent, verified before the body is parsed, carrying the message's kind, its version and both connection nonces. A worker is then admitted only if it declares the dispatcher's current build and the components the run recorded; it builds those from the RECORDED start it is sent, never from its own module's declaration, so neither a budget override nor a drifted task can change what it runs. A refusal it can verify is terminal; one it cannot is advisory, and it reconnects. Every worker process holds one lease at a time.

    Malformed MACs and bodies that cannot encode as UTF-8 refuse only their connection. MAC format validation and comparison precede body decoding. Final admission rechecks and reserves worker identity before another pending handshake can accept that ID; a distinct live incarnation is refused, while a same-incarnation reconnect retains the existing reattachment rules. Failed handoffs release only their own reservation, never another connection's ownership.

    A completed result is held before its first socket write and until an answer arrives. Read-side or write-side connection loss returns it to the external worker's existing reconnect path. An encoding failure instead becomes a completion failure and clears the pending result; it is not retried as a completed result. Protocol failures and interrupts retain their distinct meaning. An external worker holding an unanswered result refuses admission to a different run before resending or pulling work, preserving the result's issuing run identity.

    A worker that is interrupted says goodbye, and the leases it held are released with cause WorkerInterrupted while the other workers continue; a dispatcher that finishes says goodbye too, which is how an operator's worker tells a finished run from a dispatcher that died. Each spawned child is its own session, with its parent holding its standard input for life: a dispatcher that is killed outright runs no cleanup code, and that pipe closing is the only thing its children can notice. What a SIGKILL cannot reach is whatever a component started in a session of its own -- a sandboxed command outlives the worker that ran it, exactly as it outlives a single-process run that is killed. Replacing a dead worker is administration, and no worker is replaced.

    Consistency by state type¶

    Logical facts live in the run event stream; work, lease and worker state live in separate durable transactional tables. Leases cannot be ephemeral — a restart must retain the fence, deadline and accepted result — and must not live in the stream, because renewals are clock-driven: putting them there would make policy-observed versions depend on heartbeat frequency and make replay appear able to decide whether a historical lease is alive. The architecture separates committed facts from worker liveness; this record extends that into a second durable store rather than treating it as licence already granted.

    State Home Writers Guarantee
    Logical run facts Event stream and artifact storage Dispatcher only Linearizable per run. No stale read may make or accept a decision.
    Outstanding work and reserved budget Derived by folding committed events — Exact at any stream version. Never read from the work ledger.
    Work item, lease, attempt, retry Durable work tables Dispatcher and scoped lease endpoints Serializable fenced transitions. Monitoring may lag.
    Trusted worker registry Installation-level table Operator authority only Strong on registration, revocation and claim.
    Worker liveness and free capacity Ephemeral, with a TTL Workers report, dispatcher observes Stale permitted. Can never authorize a claim.
    Queue and frontier statistics Disposable cache keyed by exact versions Dispatcher Staleness only for prioritizing already-eligible work.
    Archive membership Event stream Dispatcher only Strong and replayed. Sequential only — never inside a cohort.
    Promotion External governance record Governance Strong. Consumes only a drained, validated run.

    "Strong" means one database transaction, not distributed consensus. Because attribution lives in the attempt table, the event envelope gains no actor field and no timestamp.

    The work and lease state machine¶

    States are PREPARING, READY, LEASED, COMPLETED and CANCELLED.

    The capacity inequality, which acquire names: a worker may hold at most its declared max_concurrent_leases leases at once, counted over rows in LEASED for that worker in the current epoch and generation, and the count is read inside the acquiring transaction so two simultaneous claims cannot both see room. That is the whole of it in M11 -- ONE dimension, a count of leases, not a resource vector. Per-item resource requirements and worker resource dimensions are deliberately not defined here: nothing in this milestone schedules on them, and the roadmap's acceptance case -- two concurrent claims exceeding one worker's declared capacity -- is a statement about this count and is testable against it. A richer inequality the implementation would not honour would leave that criterion with no normative behaviour behind it.

    Every acquire, renew and complete precondition includes the current dispatcher epoch and the worker's current generation, read inside the same transaction — with one exemption, which is load-bearing. Terminal duplicate lookup on a COMPLETED item checks the accepted attempt and its token but not epoch or generation liveness. Without the exemption, "commit succeeded, acknowledgment lost, dispatcher restarted" would carry the prior epoch and be answered stale, contradicting the duplicate rule below. A terminal item is a stored fact, not a live lease.

    complete is an INTENT, not a broker operation. M11.2 removed the broker's complete, whose own transaction could not be atomic with the logical batch, in favour of AcceptCompletion applied inside the writing transaction. The complete row above is unchanged in every respect that matters — the transition, and all four preconditions — because the intent carries the fence and the clock and checks them there. What moved is who applies the rule, not the rule. Moving it the first time DID drop three of the four preconditions to prose, which a review caught; they are enforced again.

    An aborted item is not marked, and nothing distinguishes it. When the abort boundary fires before the component returns, _execute re-raises without releasing or recording a cause — but expiry routes the row through released() to READY one lease-duration later, so it does return to the queue, just slowly. In the interval it is neither claimable nor reclaimable (reclaim scans READY only) and carries no terminal fact, and afterwards no reader can tell an aborted item from a flaky one. That remains true of a RESOLUTION-stage abort, which by construction spends nothing and re-aborts identically on resume.

    A completion-stage abort is split by the cause already recorded for it. No poison flag, no new state, column or migration: a fault after the component returned is recorded by record_failure against the attempt, and a resumed run reads that diagnosis rather than re-running the component to rediscover it. Only a cause recorded at the completion stage, by the attempt the row is on, is a verdict. release records an attempt failure under the same name a completion failure has, since a component may raise InvalidDecision itself, and an earlier attempt's verdict says nothing once a later attempt holds the row. A cause recorded before the stage was reads as transient: the stage rides in the column that names the cause, so a schema-4 store still opens read-only and an older cause simply has none. The deterministic set is one closed tuple — InvalidSearchHistory from folding the attempt's result, and a coordinator InvalidDecision — declared as exception types and checked positively by the type name record_failure recorded, with the name set derived from that same tuple. There is deliberately no live check beside it: nothing classifies the exception as it is caught, because the dispatcher records the cause and re-raises, and every decision about that cause is taken after a restart from the row. Declared as types all the same, so renaming or deleting a cause breaks an import rather than leaving a string quietly stale. Anything else is transient — EventStreamConflict, a bare DurableStoreError, DurableCorruption at commit, a lost lease — and re-runs, one attempt per resume, until the retry bound ends it with "exhausted N attempts". Unclassified is transient, because that fails towards a wasted attempt the bound already ends rather than towards ending an item nobody diagnosed.

    A deterministically diagnosed row is not claimable and is terminated by reclaim with an AbortWork intent beside the terminal fact its kind owes, reading "aborted: ". The filter sits at the claim as well as in reclaim, because drive() drains before it reclaims — a row left claimable would be run a second time before anything decided it was finished. Both brokers' acquire refuse such a row inside the claiming transaction, so the dispatcher's scan is not the only thing keeping it out. AbortWork re-validates inside the writing transaction that the row is READY, that it carries a diagnosis, that the diagnosis belongs to the attempt the row is on, that it was recorded at the completion stage, and that the cause is in the deterministic set; it refuses a live lease, because a lease is ended by expiry and not by an intent. This is what meets "a resumed run does not re-drive an item that aborted because it was impossible".

    The terminal duplicate exemption ships in M11.2. AcceptCompletion answers a repeated completion by replaying the stored acknowledgment rather than refusing it, checking the accepted attempt and its token and deliberately not epoch, generation or deadline. The duplicate makes the whole commit a no-op: the intent unwinds the transaction, so the row keeps its bytes and the stream does not grow.

    Duplicates remain unreachable through the dispatcher in single-process M11.2 — the batch and the intent share one transaction, a committed completion leaves the row terminal, and rollover skips terminal rows — so the exemption is exercised at the commit boundary rather than by a worker. Reattachment makes it reachable, because a connection dies with its process: M11.3 ships the submission seam that hands the replayed acknowledgment back, and the Duplicate answer with it, so a worker whose result was committed while its acknowledgment was lost is told so when it reconnects. The stale half is typed in M11.3: a stale intent still aborts its batch by design, because an intent rides the batch it authorises, and it now raises StaleCompletion carrying the one stale reason rather than InvalidWorkAppend. Only an item the run does not hold -- no lease was ever issued for it here, which is also how another run's lease arrives, since a lease names no run -- or two acceptances in one batch remain InvalidWorkAppend, a contract violation.

    From Operation Preconditions To
    absent enqueue The authorizing logical batch commits PREPARING or READY
    PREPARING prepare This trial's prerequisites are committed READY
    PREPARING preparation failed Central preparation raised CANCELLED
    READY acquire Worker matches, including the capacity inequality above; attempts remain LEASED
    LEASED renew Same worker, attempt, fence and token; before the deadline LEASED
    LEASED expire At or past the deadline READY
    LEASED release Same worker, attempt, fence and token; before the deadline READY
    READY reclaim Attempts exhausted; rides the terminal logical fact CANCELLED
    READY or LEASED cancel Dispatcher or operator authority CANCELLED
    LEASED complete Exact worker, attempt, fence and token; before the deadline COMPLETED
    COMPLETED complete again Same attempt and matching token; epoch and generation deliberately unchecked COMPLETED
    any complete with a superseded or expired attempt, or a token mismatch — unchanged
    terminal any lease operation — unchanged

    Enqueue inserts work rows in the same transaction as the decision cohort or genesis. Completion validates, appends the logical batch, enqueues dependent evaluation work, and stores an acknowledgment — all atomically.

    The exhaustion edge was split in M11.2 (M11.2, implemented). This table originally read LEASED --expire at retry limit--> CANCELLED. Three broker-side transitions produce an unfinished lease — expiry, rollover and release — and none of them is committing a batch, so none can carry the terminal logical fact this record's sixth rule requires. A row terminated there would be terminal with nothing in the stream saying why, and nothing that would ever revisit it. All three now release to READY; the acquire guard (attempts < max_attempts) makes an exhausted row unclaimable, and the dispatcher's reclaim step terminates it with TerminateWork alongside the fact in one logical commit. The observable end state is unchanged; what moved is who owns the edge, so that it can carry its fact — and a crash between exhaustion and the fact now leaves a reclaimable row rather than a permanent silent hole.

    The rules the table encodes:

    • The deadline is half-open. Completion and renewal succeed only strictly before it, read from the broker clock inside the transaction.
    • An expired but unreclaimed attempt may not submit a completion. Expiry follows from the clock read, not from whether a replacement exists. Its one remaining write is its own diagnosis, under record_failure's rule.
    • Duplicate is not stale. The same attempt with a matching token returns the original acknowledgment. Anything else is stale. Neither is an error, and neither writes.
    • Renewal racing expiry resolves in one transaction; the loser is stale.
    • Revocation bumps the worker's generation, invalidating its leases at the next transactional check.
    • Retry exhaustion, preparation failure and cancellation each append the terminal logical fact for their work kind — never a ledger-only edit.

    Clock domain. Deadlines are absolute broker timestamps from a single authority; workers never decide expiry from their own clocks. The broker persists its last observed time and clamps its clock non-decreasing, so a rollback within an epoch cannot un-expire a lease. Across a restart the dispatcher epoch is bumped, and rollover is an explicit recovery step: every prior-epoch leased row moves back to ready, or is cancelled with its terminal fact when attempts are exhausted. Rows are never left unclaimable.

    A rollover supersedes whoever held the epoch before it. The dispatcher that rolls over fences its coordinator with the epoch rollover returned. Every logical commit it then makes carries a RequireEpoch intent, checked first among the intents inside the writing transaction, and every broker write — acquire, renew, renew_or_stale, release, record_failure, cancel — takes the same epoch. Each compares the dispatcher-held epoch with the stored one, never with a lease's; on a mismatch it raises DispatcherSuperseded and writes nothing. A rollover writes no event, so without this a superseded dispatcher's projection would still be current and its commits would pass the stream's own concurrency check. Genesis and runs that never roll over hold no epoch and are not fenced. This is exclusion, not failover: nothing decides which dispatcher should win.

    Outstanding work and the decision barrier¶

    Everything else keys off one definition. A trial is outstanding when it has a committed trial decision, or is the bootstrap trial, and either it has no completion, or its completion succeeded, its evaluation disposition is evaluate, and no evaluation has completed.

    The bootstrap satisfies that second clause by exception, not by pin. It is never pinned a disposition — its evaluation is owed by genesis rather than authorized by one — so read literally the clause would exclude the very trial the first clause names, and a distributed genesis would leave no committed fact saying the evaluation is owed. The bootstrap is therefore outstanding while it has no completion, or a successful completion with no evaluation, and its disposition is not consulted.

    The second clause is what distinguishes a trial that still owes an evaluation from one whose evaluation was terminally skipped as unauthorized. Treating every successful completion as terminal would accept a stop while an authorized evaluation is pending; treating none as terminal would reject a legitimate stop after a skip.

    The disposition has three values, not two. Evaluate and terminally skipped are the two answers; the third is no answer — recorded for a failed trial, for the bootstrap, and for a trial whose own recorded usage exceeds its own allocation. The last of those is what makes the other two usable: with only two values, an overrun would have to be recorded as skipped, and the fold refuses an evaluation on a skipped trial, so every historical over-budget stream would stop replaying. Leaving the question unanswered where it is ill-posed is what lets skipped mean only "terminally skipped" and be enforced. A trial with no answer is not outstanding, so it neither holds a stop nor is owed anything — except the bootstrap, which is no-answer and outstanding at once. That is the one place the two come apart, and it is why the outstanding-work definition above names the bootstrap separately instead of relying on the pin.

    A policy decision may be committed only when nothing is outstanding, or when the decision is a trial decision, every outstanding trial shares its cohort base, that base equals the stream head immediately before the cohort's first decision, and the decisions carrying that base form one contiguous run ending at this one.

    A stop cohort has length one, so it can only be admitted through the empty branch. At width one nothing is ever outstanding at decision time, so the rule is today's sequential guard verbatim.

    Consequently two shipped rules need no change at all: a committed stop remains an absolute terminator, and a run with a committed stop is complete. Observation cutoffs are likewise untouched, because context and experience are refused under distribution.

    Generational cohorts¶

    An opted-in policy declares a cohort width and returns a cohort: a non-empty tuple of trial decisions produced from one complete committed history and committed as one atomic batch. Absence of the capability means width one and today's sequential decision.

    Composition. Either a tuple of trial decisions bounded by the declared width, or a singleton stop. Mixed forms are invalid, and archive updates are never part of a cohort.

    No truncation. The coordinator commits the whole cohort or refuses it entirely, as trial validation refuses rather than trims today. Sizing a cohort to what fits is the policy's responsibility, and it has the state to do it.

    Width is declared, and reaches run identity by kernel derivation. A policy supplies its identity key independently of its configuration, so a conforming policy could record a wide cohort and still return the narrow key. The kernel therefore contributes the width itself, omitted at width one so every recorded run identity is unchanged. Any cohort-capable policy also exposes its width in durable configuration, likewise omitted at one, so the fold can bound cohort length with no live registry. The sequential path refuses a width above one, since without that refusal one declaration would stop early sequentially and run wide distributed under a single run identity.

    Replay. Each decision still records the stream head immediately before it, so no field is ever false; what the policy observed is recorded separately as the cohort base. Consumers reconstructing a policy's input from the recorded head must switch to the base for members after the first, beginning with the search-program replay law. Replaying a cohort from its base must reproduce the committed tuple exactly.

    Conformance. A published cohort suite carries the laws: composition and length, full-or-refuse, exact replay from the base, per-member randomness attribution, no member referencing another member's artifact, width present in configuration exactly when it exceeds one, and a width-one coherence law requiring a singleton cohort to equal the sequential decision. Passing a suite is a developer obligation, not a durable fact: the executable admission predicate is the structural declaration, and the suite is what makes it honest.

    Budget: one disposition, and a pure fold¶

    Reserved budget is derived from committed events, never stored: any capacity freed outside the stream would make a later decision unreproducible.

    One evaluation disposition, consumed by every caller. At a successful trial completion, over the prefix including that event, available capacity is the ceiling less settled usage less the reservations of every trial except this one. Excluding the completing trial's own allocation breaks the circularity — an incomplete sibling reserves its full allocation, and a completed one was resolved at its own earlier terminal event.

    Two terms survive from the shipped calculation and are not replaced by the reservation fold. The trial's own remaining allocation still narrows the result, so a trial that exhausted its own budget is skipped even where the run's capacity is ample. And spend is adjudicated against the trial's own charge, so a free proposal under a zero ceiling still evaluates. The disposition is therefore the run's available capacity narrowed by the completing trial's remaining allocation, authorized when the narrowed budget leaves no zero among its evaluation, token and wall-time allowances and spend is not exhausted against that trial's own charge. The fold adds a term to the shipped rule; it does not replace it. Anything looser would flip committed skip decisions into evaluations and move durable bytes.

    That rule is only consulted where the question is well-posed. A failed trial, the bootstrap, and a trial whose recorded usage exceeds its own allocation are pinned no answer instead — see outstanding work for why the third value is what makes the refusal on a skipped trial enforceable.

    That value is pinned at one event, so it is stable for all later prefixes, which is what makes live execution and recovery agree by construction -- and agreement means every reader consults the pin rather than re-deriving it. A reader that recomputed the overrun instead would call a stream corrupt that this fold has just declared replayable, which is exactly the contradiction #217 resolves in the fold's favour. Five callers consume it: the live completion path, the resume tail, the recovery frontier classifier, the outstanding-work definition, and the dispatcher's atomic accept-and-enqueue path. The general remaining budget keeps its meaning for admitting new trials but is no longer a valid input to evaluation authorization.

    A trial reserves its full allocation until it completes, its evaluation residual while an authorized evaluation is owed, and nothing once it has failed, been terminally skipped, or had its evaluation complete.

    Erratum (M11.2). This paragraph originally continued "The bootstrap trial follows the same rule", and that is the same mistake the errata above correct in two other places: the bootstrap's evaluation is owed by genesis and is never authorized by a disposition, so under the unamended wording a completed bootstrap reserves nothing — which the table's own last two rows deny. The bootstrap reserves on the same schedule as any other trial but on a different authority, and the fold needs two explicit branches for it rather than none. What does carry over unchanged is the reason it needs no special allocation: no policy decision may be committed before the run is ready, so its reservation is never concurrent with a cohort.

    Trial state Reserved Released by
    Decided, no completion committed Its full declared allocation Its own terminal fact
    Completed, evaluation authorized and owed, other than the bootstrap trial Its evaluation residual: the allocation less the usage already settled against it The evaluation completion, successful or failed
    Completed, evaluation terminally skipped Nothing Already released by the completion itself
    Completed, disposition unanswerable, and not the bootstrap Nothing Already released by the completion itself -- nothing can be owed against a question the fold refused to answer
    Failed proposal work Nothing Its trial completion carrying the failure
    Failed evaluation work Nothing Its failed evaluation completion, never a second trial completion
    Failed before any proposal — preparation failure, cancellation, retry exhaustion Nothing The full shipped failure batch
    Bootstrap, decided, no completion committed Its full allocation Its evaluation completion
    Bootstrap, completed, evaluation owed Its evaluation residual Its evaluation completion

    These rows are a partition: every trial state matches exactly one row, and a failure releases through the one mechanism its work kind names.

    The dimensions are not interchangeable, and the reservation fold governs only two of them:

    Dimension Finite under distribution How admission uses it
    trials, evaluations Admitted — the only finite dimensions M11 serves The exact reservation fold above
    tokens, wall_seconds Refused finite at start Nothing until #206 defines a per-trial share
    spend_micros Refused finite at start, zero included Never a reservation. Budget.spend_micros is a ceiling that halts, not a hard cap, so it has no prospective form to reserve against

    Every capacity release is a committed logical fact whose kind differs by work kind: proposal work terminates with a trial completion, evaluation work with a failed evaluation completion, never a second trial completion. Work that never produced a proposal — preparation failure, cancellation, retry exhaustion — commits the full shipped failure-batch shape rather than a bare completion.

    Exactness, in three parts. Admission is exact over committed facts. A component may still overrun its allocation, which commits as a typed resource exhaustion with its actual figures and halts the run — shipped single-trial behaviour, not a concurrency regression. And consumption is exact only over accepted completions: a stale or orphaned attempt writes nothing by design, so what it consumed never reaches the run's usage. That gap is new to distribution and is documented rather than papered over.

    A monetary hard cap additionally requires provider-side idempotency and bounded spend authority. Declaring a component retry-safe is necessary but not sufficient: it says reinvocation is logically safe, not that billing is idempotent.

    A finite spend ceiling is refused at distributed start, zero included — and zero is the one monetary declaration with nothing to allocate, since spend_exhausted reads it as free-work-only and arms only once something bills. Refusing it therefore refuses a configuration cohorts could otherwise serve. The refusal stays blunt deliberately: at width N a zero ceiling admits up to N charges before the halt arms where the sequential path admits one, and weakening a declared prohibition by the cohort width is a worse thing to ship than a missing capability. #206 is where per-dimension allocation earns the right to separate them.

    Worked traces¶

    Each trace is a step sequence over the two ledgers, written so an implementation can be checked against it without re-deriving the rules above. W is a work item, t the broker clock.

    Lease expiry, and the replacement that supersedes it¶

    Step t Event stream Work table
    1 0 The trial decision commits W inserted READY, attempts 0, in the same transaction
    2 0 — Worker A acquires: LEASED, attempt 1, fence 1, deadline 30
    3 25 — A renews: deadline 60, same fence
    4 61 — A is silent. The next transactional read finds the deadline passed: LEASED → READY, attempt 1 abandoned
    5 62 — Worker B acquires: LEASED, attempt 2, fence 2, deadline 91
    6 70 — A returns and submits under attempt 1, fence 1
    7 70 — Stale: the fence does not match. Nothing written, nothing raised
    8 80 The trial completion for B's result, and the dependent evaluation item, commit together W → COMPLETED, accepted attempt 2

    One logical trial throughout; the retry created an attempt, not a trial. Whatever A consumed — tokens, and any charge it incurred — never reaches the run's usage. That is the documented consumption gap, not an accounting defect.

    At step 4 expiry follows from the clock read alone. Had B never arrived, A's submission at step 6 would still be refused: an expired but unreclaimed attempt may not submit.

    Duplicate versus stale submission¶

    Both arrive at a COMPLETED item. The columns are the two OUTCOMES, not a partition of the inputs, and the difference matters: the accepted attempt carrying a mismatched or absent token matches neither column as written. The state machine classifies it stale (complete with a superseded or expired attempt, or a token mismatch), and it must, because the token is what proves the submitter is the worker that earned the attempt. A duplicate is therefore the accepted attempt AND a matching token; everything else at a terminal item is stale.

    Duplicate Stale
    Attempt The accepted attempt Any other attempt
    Token digest Matches Mismatched or absent
    Epoch and generation Not checked — the terminal exemption Not checked
    Answer The original acknowledgment, replayed A stale answer
    Writes None None
    Raises Nothing Nothing

    The table is the answer a submitting worker receives. Inline the same stale submission RAISES, as StaleCompletion carrying its stale reason, and aborts the drive; a duplicate is unreachable inline, because a committed completion ends the dispatcher's use of that lease.

    The exemption is load-bearing exactly once — when the acknowledgment is lost across a dispatcher restart:

    Step Event stream Work table
    1 The completion batch commits W → COMPLETED, accepted attempt 3, acknowledgment stored
    2 — The reply to the worker is lost in transit
    3 — The dispatcher restarts; the epoch is bumped; prior-epoch LEASED rows roll over, and W is untouched because it is terminal
    4 — The worker retries attempt 3 with its token
    5 — Terminal duplicate lookup matches attempt and token, ignores the stale epoch, and replays the stored acknowledgment

    Without the exemption step 5 would answer stale, and a worker would believe committed work was lost.

    Bootstrap evaluation¶

    Step Event stream Work table
    1 Genesis commits the run start, the seed artifact and the bootstrap trial The bootstrap evaluation item is enqueued in the same transaction
    2 — The bootstrap trial has no proposal item; it is the one trial whose only work is evaluation
    3 — A worker claims and completes it under the ordinary state machine
    4 The bootstrap evaluation commits, and the run becomes ready W → COMPLETED

    Between steps 1 and 4 the run exists and is not ready. Inspection is available and returns the shipped overview fields without raising; no policy decision is admissible. That is why the bootstrap reservation is never concurrent with a cohort, and why it needs no special allocation rule.

    Cohort admission refusal¶

    Refusal has two independent shapes, and neither trims.

    Step Declared width Policy returns Outcome
    1 4 Five trial decisions Refused whole. Length above the declared width is invalid, and the coordinator does not keep the first four
    2 4 Three trial decisions and a stop Refused whole. Mixed forms are invalid; a stop cohort is a singleton
    3 4 Four trial decisions, one referencing another member's artifact Refused whole. No member may reference a sibling, which has not been committed

    The barrier refuses on a different axis — the decision's provenance rather than the cohort's shape:

    Step Stream state Decision offered Outcome
    1 Nothing outstanding A trial cohort based at the head Admitted; this is the empty branch, and it is today's sequential guard verbatim
    2 Two trials from that cohort outstanding A further trial decision on the same base Admitted only while the decisions carrying that base form one contiguous run ending at this one
    3 Two trials outstanding A stop Refused. A stop cohort has length one and can only be admitted through the empty branch, so a stop with work outstanding is rejected
    4 Two trials outstanding A trial decision based at a later head Refused. The base no longer equals the head immediately before the cohort's first decision

    The seven distributed-start refusals¶

    Every row raises CapabilityError, naming its reason, before any claim or lease is issued. Single-process distributed resume ships in M11.2: prepare_resume admits a distributed run, re-runs admission against the recorded values, and Session.drive() rolls the epoch over as the explicit recovery step. There is no Dispatcher.resume — resume is Session.resume(...) followed by drive(). Cross-process re-read stays M11.3's.

    Of the seven, one is genuinely re-checked on resume against a value that can drift: the cohort capability, because the program is re-resolved from the supplied registry. Context, experience, budget and codec are read from the committed start and cannot change, so their resume-side refusals are store-tampering backstops rather than admission re-checks; the codec row is enforced by check_declared_codec on every reader's path.

    Six of the seven are enforced, and the seventh is a different KIND of rule. The fingerprint row is recorded and not compared — see environment fingerprint — and it could not be compared at start or at resume even once that lands, because a worker's fingerprint is not part of the run declaration and no worker exists yet. It is the one refusal that fires when a worker IS ADMITTED, before it can claim, and it refuses the worker rather than the run.

    resumable means the run recorded enough identity to resume, not that it replays identically. For durable-local the two coincide, because its components are deterministic by admission. A distributed run may carry a non-deterministic component — a model-backed proposer is the ordinary case — and resuming one continues the search rather than reproducing the trajectory it would have taken uninterrupted. That is the schedule-sensitivity this record already states, made explicit at the flag that would otherwise imply more.

    Refused Read at start from Re-read on resume from
    A declared context policy The run declaration's context policy The committed run start
    A declared experience access The run declaration's experience access The committed run start
    A policy without the cohort capability The supplied program's structural declaration The re-supplied program's declaration, cross-checked against the recorded configuration
    A finite token, wall-time or spend ceiling The effective budget: task and run declarations narrowed The committed task and run capabilities
    A custom codec The declared artifact codec The committed run capabilities
    A component not declaring retry_safe Every resolved component manifest The manifests re-resolved for the recorded refs
    An environment fingerprint mismatch Not at start: a worker's fingerprint is not in the run declaration and no worker exists yet Not at resume either. This one is checked when a WORKER IS ADMITTED, before it can claim, against the dispatcher's current build, and refuses the worker rather than the run

    Resume is the strictly harder direction: a run admitted under a conforming program can be resumed with a program that no longer declares the capability, or in an environment that has drifted since, and neither is visible from committed history alone.

    Determinism¶

    Ranking keeps score primary: evaluations are pre-ordered by their producing trial's logical step, then stably sorted by score, with the evaluation id as a final tiebreak — so a later better score still wins and only exact ties are decided by logical order. On sequential streams logical order equals completion order, so existing runs are unchanged.

    A cohort barrier makes the set of results visible at the next boundary independent of arrival order, but not the policy's view of them, because policy-facing collections remain in commit order. Either those collections are canonicalized by logical step, or the cohort suite carries a completion-permutation-invariance law. This record chooses canonicalization, for the same reason width is kernel-derived: a structural guarantee beats a trust-based one, and a policy should not become schedule-sensitive by accident.

    Canonicalization lands where each collection is built, not where it is read. The completed trials and evaluations are ordered at insertion by their producing trial's logical step, with the evaluation id as the final tiebreak.

    The artifact list is ordered later than the others, and for a structural reason: an artifact is committed before the completion that attributes it, so at insertion there is no producing trial to order by. The completion carries both the artifact ids and the logical step and lands in the same batch immediately after, so that is where the list becomes canonical -- and the seed attributes to the bootstrap at step zero. Reading order out of the projection instead would put a sort on the fold's hot path, which the reserved-budget fold already showed is where cost accumulates.

    Retry exhaustion remains a genuine divergence no ordering rule removes, since scheduling decides whether a completion lands inside or outside its deadline:

    A distributed run reproduces every decision and named random choice from its committed history. Repeating the same declaration and seed reproduces the same trajectory only when every outcome is itself deterministic and no attempt is abandoned — a non-deterministic provider or a lease that expires under load will diverge. A cohort barrier guarantees that the set of results visible at the next boundary does not depend on arrival order.

    Environment fingerprint¶

    A versioned digest over the interpreter implementation and version, the platform, the resolved distribution set, and the installed Meta-Evolve source digest, recorded on the run's capabilities and declared by every worker; mismatch refuses the worker.

    M11.3 compares it at ADMISSION, against the dispatcher's CURRENT build. A worker process declares its fingerprint in the handshake, and one that differs is refused before it can claim anything — the refusal names the worker, never the run, and the other workers are untouched. That is the shape the comparison always had to take: comparing fingerprints is part of admitting a worker, not part of handing out a lease, so neither broker's acquire reads worker.environment_fingerprint and the value a WorkerRegistration carries is informational.

    M11.4's durable worker table makes the admitting authority durable; it does not move where the comparison happens.

    A RESUME-TIME comparison is a different question, and it remains deferred for a different reason. M11.3 compares a worker against the build it is about to serve, which is a same-build check with one honest answer. Whether a RUN may resume on a build that has moved is a policy question, not an authority one. On resume both values are already in hand — the recorded fingerprint on RunCapabilities, and the current one from environment_fingerprint() — so nothing about worker-table authority blocks comparing them. What blocks it is what the digest covers: the installed meta-evolve SOURCE and every installed distribution. Measured: changing the source digest, adding one unrelated package, or a patch-level Python bump each move the fingerprint. A strict resume-time comparison would therefore refuse every legitimate resume across a code change or a uv sync — which in this repository is the ordinary case, not the exception, since evolving the source is the point.

    So the open question is not authority but POLICY: which dimensions must match for a resume to be safe. Platform and interpreter plausibly must; the source digest plausibly must not, or the flag means "resume only the exact build that started this run". Whoever implements #203 should decide that before writing a comparison, rather than discovering it from a refused resume.

    It is a version-set fingerprint, not environment identity. Name and version pairs do not identify installed bytes, so two editable or locally patched installs can match, and the platform string omits OS release and libc ABI. It reliably detects drift; it does not prove sameness. Content-hashed distributions are the exit.

    Decisions¶

    Central decision authority with generational execution — one dispatcher is the sole caller of the policy and the sole writer of the stream. Two ledgers, with lease state durable but outside the event stream. Attempts distinct, not secret, with the lease token and fence carrying authority. Reserved budget as a fold, every release a committed fact. One evaluation disposition, pinned at completion, consumed by all five callers. Cohort width declared on the policy and contributed to run identity by the kernel. Policy-facing collections canonicalized by logical step. The sequential path refuses a width above one. A dispatcher is fenced by the epoch its own rollover returned, so a superseded one writes nothing more. An aborted item gains no state, column or migration of its own: the cause its current attempt recorded at the completion stage decides what a resume does with it. The broker host runs inside the dispatcher process, which stays the sole writer of the store. Execution is at least once, inline as on a worker; acceptance is at most once. A worker process is admitted by a mutually authenticated handshake against the dispatcher's current build before it can claim. Spawned workers finish admission before the epoch rolls over; external workers join during the drive. Reattachment preserves acceptances, not work.

    Deferred and rejected¶

    Deferred. Steady-state refill, which admits new work while earlier work is outstanding: it does strictly more than cohorts, is not asked for by #10, and costs a general pending-work capability, a post-stop drain rule, a changed completeness definition, and per-policy conformance. Distributed context and experience, which need a cohort-aware prerequisite grammar, a reconciled cutoff, and an endpoint carrying an operation ordinal with attempt and resolution appended atomically. Concurrency for further presets, each behind proved pending-work semantics. Paid concurrency, behind conservative per-trial allocation.

    Replacing a worker that died, and a worker capacity above one, both belong with worker administration (#203, #204): a run whose spawned workers have all died is refused by name so that resuming it is the operator's decision. Killing the sessions a component started for itself, after its worker is killed outright, needs a process-wide registry of them for a watchdog to read — which is the hidden global state the constitution rules out — and the gap is the one a killed single-process run already has.

    Rejected. Decentralized policy decisions; leases in the event stream; workers appending envelopes; reservation rows outside the stream; releasing capacity without a terminal fact; redefining what a decision's recorded head means; cohort width as an execution overlay; truncating a returned cohort; mixed-kind cohorts; archive updates inside a cohort; policy-specific coordinator branches; a trial id serving as both work identity and lease credential; secret or random attempt identities; completion-order tiebreaks; running every policy concurrently by default; adding a distributed mode to the synchronous callable path; actors or timestamps on the event envelope; external queue dependencies; multi-dispatcher consensus or failover; a heartbeat-receiver thread, since a timestamp renews nothing and the renewal would still queue behind the commit; encoding inline results as frames; an in-process registry of running calls, which could only be process-global state; a batch renewal operation, for one write where the per-lease calls cost a handful; a live rebind of a lease issued before a dispatcher restart, which the epoch fence makes impossible without weakening it; a worker capacity field whose only legal value is one; and admitting spawned workers lazily, which would let a failed handshake cost a run its epoch.
