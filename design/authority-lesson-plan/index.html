    Fixed evaluation: plan for #352¶

    Status: Design—not shipped.

    Prepared September 21, 2026 for #352, D8 under #343. The dependency #351 is open. Its help-assistant lesson and verification record are present in the working tree; Salah's review and publication remain outstanding. Planning can overlap; acceptance follows the dependency order.

    The implementation verification records the delivered lesson, installed Jupyter runs, and remaining review.

    The programming model owns the API and refusal contract, the architecture owns authority, and the M8 acceptance record and implementation boundaries describe the existing harness mechanism. M11 remains the runtime build boundary. This work teaches shipped behavior.

    Reader outcome¶

    Answer: “What stops a proposed change from changing the test instead of improving the answer?” Reuse D7's help assistant, password/invoice notes, and three fixed questions. Readers should point to the editable instruction, the protected checks, a permitted mistake, and a retained refusal before learning the broader ownership terminology.

    Use one bounded run, one evaluator, and three proposed revisions. Keep the starting exact-match instruction and the same two supported worker behaviors. The second revision deliberately restores exact matching after the first revision broadens it; its missed polite question is an ordinary measured error.

    Record Proposed change Expected measurement Evaluator called?
    Starting version Match exact questions. 2/3 checks Yes
    Allowed improvement Planner value becomes Match topic words. 3/3 checks Yes
    Allowed regression Planner value returns to Match exact questions. 2/3 checks Yes
    Forbidden declaration change Rename the planner surface to evaluation_checks, with a proposed always-pass rule PolicyViolation; no score or successor artifact No

    The last proposal attempts to redefine what the editable field means. It does not obtain or modify the actual evaluator. Show the proposed renamed field beside the original declaration and the unchanged HELP_CASES; do not describe this as executing a replacement grader or protecting against arbitrary Python.

    Expected work: three proposal attempts and three evaluations, including the starting version. The refused attempt adds one proposal and zero evaluations. Three questions within one evaluator call are three checks, not three accounted evaluations. The best measured instruction remains topic matching, even after the regression and refusal. Use no satisfaction threshold that would stop the demonstration after reaching 3/3.

    Enforce the actual boundary¶

    Use the existing meta_evolve.harness.HarnessArtifact, with TextParam and PolicyParam. Schema v1 requires both planner and context-policy parameters; show both definitions. Explain that both values are declared mutable, although this example only exercises the planner value. Do not claim that this artifact declares a planner-only allowlist.

    The permitted proposals can use HarnessMutation and HarnessArtifact.apply. For the forbidden proposal, deliberately bypass that convenience method and construct a successor with dataclasses.replace: change planner.name to evaluation_checks and its value to an always-pass instruction. The core's generic successor-validation hook calls HarnessArtifactCodec.validate_successor after encoding and before creating a successor artifact. It rejects the changed declaration with PolicyViolation and changed_declarations=("planner.name",) before evaluation.

    This distinction matters: apply(HarnessMutation("evaluation_checks", ...)) instead returns InvalidOutput for an undeclared surface. That helper is convenience, not the authority boundary. Keep the main three-case demonstration on the core refusal; an existing helper test or a short explanation can cover the other failure kind without a fourth required case.

    Use Task(artifact=harness.HarnessArtifact, ...), Experiment, and run(). improve() does not select this artifact codec. Declare a three-attempt allowance and up to four evaluations, permitting the seed and every proposal if all were admitted; the refusal leaves one evaluation unused. Use bounded Greedy search so the third attempt still has the successful instruction as its parent. Reset the authored proposal sequence when the run cell is rerun.

    Keep notes, cases, evaluator callable, objective, and budget outside the candidate. The worker must interpret instruction text and return actual answers; the evaluator must retain question, expected answer, actual answer, and pass/fail evidence. Never assign quality from a revision label. Derive the displayed scores, failure reason, selected instruction, and counts from the returned run records. Display the failed record's lookup so readers can locate it again and inspect its .id, without treating a content duplicate as the same occurrence. This keeps the transcript readable without pinning an opaque identifier across package revisions.

    State the limits beside the result:

    • This is a deterministic in-process simulation. Declaration validation supplies no process, filesystem, or Python security isolation.
    • The refusal protects immutable harness declarations on the normal proposal path. The actual checks remain experiment-owned; arbitrary malicious Python could access notebook globals and is outside this demonstration's protection.
    • Preventing this forbidden edit does not prevent all exploitation of an imperfect metric. Broader specification-gaming research stays in #216.
    • A path-valid SourceTree does not enforce a file allowlist. This notebook needs no source-tree variant, confinement setup, provider, or new framework.

    Notebook and page¶

    Add one complete canonical source at examples/learn/harness_authority.py. Adapt D7's small worker and fixed cases directly, with no runtime sibling imports or hidden helper definitions. The page and downloads must use this source's snippet sections; avoid a second hand-maintained notebook program.

    Target five required cells, including installation, each below 40 lines:

    Cell Visible contents
    1 Shared Python 3.12+ installation cell and fresh-kernel guidance
    2 Imports, fixed notes/cases, and the complete two-instruction worker
    3 Typed seed, both surface declarations, and evaluator with retained checks
    4 The three explicit edits and proposer that returns the next successor
    5 Reset sequence, declare/run experiment, inspect outcomes, protected checks, selection, and exact counts

    Use readable definitions rather than compressed statements to fit the limit. Count output comments as cell lines too. If the full inspection is too large, keep the first measured result within five cells and make any additional required inspection cell explicit in the evidence; do not hide setup to meet the count. Prefer fitting all three outcomes within the five-cell target.

    Put the example early in docs/concepts/authority.md, retaining its URL, keep-authority-where-it-belongs, ownership explanation, and promotion section. Preserve existing useful heading fragments. Add a D7 link next to its statement that the fixed checks stay outside the revised configuration; distinguish the plain mapping there from this typed declaration.

    After the result, give one small “Change and predict” exercise: replace the forbidden edit with a permitted planner-value change and rerun. It should reach evaluation and use the fourth evaluation, even if its answers are wrong. Choose a non-no-op instruction relative to the current best parent. This makes the difference between admission and quality observable.

    • Execute the exact displayed cells: retained scores are 2/3, 1, 2/3, followed by policy_violation with empty metrics and no successor artifact/evaluation. The successful topic-matching version remains selected.
    • Instrument evaluator entry in a focused test: only the seed and two admitted revisions enter it. Prove the forbidden successor reaches the core check, rather than returning a manually constructed failure from the proposer.
    • Assert exact aggregate usage and per-attempt count changes. Confirm the second revision has its own artifact occurrence and parent link even though its content returns to the starting instruction.
    • Snapshot the fixed cases, notes, evaluator declaration, budget, and original harness declarations; verify they remain unchanged through every attempt. Every retained evaluation must use the same expected answers. Also cover direct component/interface declaration replacement with the existing harness regression suite.
    • Exercise the documented permitted replacement for the forbidden edit: evaluations rise from three to four; ordinary poor answers remain measured. Changing an expected answer as the experiment author changes the score in a separate control, proving the checks actually determine the measurement.
    • Whole-notebook and final-cell reruns reset the sequence and reproduce the outcomes without StopIteration or prior notebook state.
    • Check source, rendered Python cells, and generated notebook parity; visible definitions; cell lengths/counts; download links; and retained page anchors. The authority page contains a text diagram, so filter Python blocks rather than assuming every HTML pre is an executable cell.
    • Run downloaded Python, notebook cells, and rendered copied cells against a fresh noneditable install outside the checkout, with package-origin checks, no repository imports or provider keys, and no runtime network access.
