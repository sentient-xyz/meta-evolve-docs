    Meta-Evolve Milestones¶

    The current runtime build boundary is M11: distributed execution defaults to inline calls and supports explicit trusted-worker process backends. The separate author API release gate coordinates 0.2 publication. Completed stages below link to current contracts instead of repeating their implementation checklists.

    The programming model owns shipped API behavior, architecture owns invariants, and the implementation plan owns technical boundaries.

    SoL-Pi: harness efficiency experiment¶

    Status: Design—not shipped. This research follow-up translates SoL-Pi, v1 into a bounded local experiment. It builds on shipped harness evaluation, source artifacts, experience, and resource accounting. M11 remains the runtime build boundary; this item adds no concurrency or release prerequisite. The implementation plan owns its technical composition.

    Goal¶

    Use execution evidence to propose agent-harness changes that reduce cost while keeping each capability metric within a fixed tolerance. Evaluate the frozen selection against the unchanged baseline on held-out tasks. The experiment owns metrics, tolerances, splits, models, environments, budgets, and promotion.

    Ordered scope¶

    1. Deterministic local proof. Reserve examples/research/sol_pi/ for a small callable experiment with a fixture runner. Version a validated configuration, retain development observations, and demonstrate capability-constrained efficiency selection. Exercise Action Fusion (edit plus follow-up command) and ObservationPack (bounded context with exact output recall) before adding other mechanisms.
    2. Opt-in runtime integration. Wrap a pinned version of the authors' Pi extension through user-owned execution code. Compare the baseline, individual mechanisms, and their combination under equal external controls. Add Evidence-Preserving Reducer and Online Context Compact only with verified evidence handling, compaction lifecycle, and complete auxiliary-call accounting. Live results remain Experimental/live-only and retain ties, regressions, and failures.
    3. Later research scope. Evolve allowlisted harness source after the configuration experiment passes. Large concurrent campaigns depend on M11 and its paid-work reservation/settlement gate; they are not part of the local proof.

    Acceptance gate for the local experiment¶

    • Candidate configuration has an explicit allowlist. Independent validation rejects changes to evaluator controls, permissions, budgets, or promotion.
    • Selection first checks every declared capability tolerance against the fixed baseline, then requires improvement in at least one declared efficiency metric. Retain nondominated eligible candidates under explicit metric directions and deterministic tie-breaking; do not substitute Specialists or the primary-objective compare_harnesses verdict for this rule.
    • A cheaper candidate outside a capability tolerance is rejected. A cheaper candidate at equal quality can be retained. Invalid, incomplete, or failed executions remain typed, non-rankable outcomes with their incurred costs.
    • Development evidence alone informs proposals and selection. Freeze the selected artifact, metrics, tolerances, and comparison rule before fresh held-out baseline/candidate executions; held-out feedback never returns to search, and rejection cannot trigger another optimization round.
    • Retain per-task quality, raw usage, billed spend when known, model and runtime identities, and mechanism activations. Preserve cache-read/write and auxiliary-model breakdowns when available; estimates remain evidence, unknown spend remains unknown, and nested work is charged exactly once.
    • Tests cover fused-action failure boundaries, exact observation recall, selection and dominance cases, split isolation, and accounting. Committed candidate lineage, evidence, failures, and selection decisions replay without provider execution. An entirely failed search still has an inspectable report.
    • A short runnable example, documentation, and an unchanged-baseline comparison establish the mechanism. Neither a positive live gain nor replication of the paper's savings is required to demonstrate the local boundary.

    Out of scope¶

    A first-party agent runtime, new built-in HarnessArtifact surfaces, a generic Pareto framework, unrestricted self-modification, automatic deployment, the paper's full benchmark scale, and claims of compounding recursive improvement. Create no placeholder example tree before implementation begins.

    SIFT: judge-guided agent evolution¶

    Status: Design—not shipped. This research example adapts Self Improvement via Fast Tree-search (SIFT), v1 to the shipped local engine before pursuing the paper's asynchronous pipeline. M11 remains the runtime build boundary; this example adds no release prerequisite. The implementation plan owns its technical composition.

    Goal¶

    Evolve versioned coding-agent source using pairwise judge preferences and independent development measurements to guide parent selection. Compare the frozen selected agent against the unchanged baseline on held-out tasks, retaining the evidence and costs needed to assess whether judging helps search.

    Ordered scope¶

    1. Deterministic sequential proof. Reserve examples/research/sift/ for an allowlisted SourceTree experiment with fixture proposers, pairwise judgments, and independent execution. Include an easy-task gate, bounded comparison-target selection, regularized Bradley–Terry fitting, and parent sampling from judge rank, measured accuracy rank, and parent visit counts. Complete each admitted candidate's development evaluation before the next expansion. Label this a sequential adaptation, without asynchronous speedup or full SIFT reproduction claims.
    2. Opt-in live experiment. Supply user-owned model wrappers and a pinned benchmark adapter with isolated execution. Compare judge-guided search to an accuracy-only ablation under equal external controls and total budgets, including judge costs. Live results remain Experimental/live-only; report ties, regressions, failures, and unknown spend.
    3. Deferred asynchronous reproduction. Separate expansion and evaluation queues, speculative descendants, provisional inherited accuracy, and priority updates require an explicit runtime acceptance gate beyond M11's generational cohorts. Depend on trusted concurrency and paid-work reservation/settlement where applicable; completing M11 alone does not supply these semantics. This stage is outside the local proof.

    Acceptance gate for the local experiment¶

    • Candidate changes are confined to declared agent source. Evaluators, task splits, judge configuration, budgets, permissions, and promotion remain experiment-owned. Judges receive candidate implementations or recorded diffs, without benchmark tasks or outcomes; proposers may receive declared development diagnostics.
    • Retain comparison targets, pairwise outcomes, model/configuration identities, artifact occurrences, and decision order. Recompute archive-wide strengths from recorded wins and losses; pin regularization, convergence, rank ties, visit accounting, and named randomness so selection can be reconstructed.
    • A deterministic fixture demonstrates that the judge signal changes parent selection against the accuracy-only ablation. Tests cover sparse comparisons, ties, gate rejection, judge failure, and disagreement with measured accuracy. Failed measurements remain typed outcomes, never synthetic scores or wins.
    • Keep judge preferences, derived strengths, and measured accuracy distinct. Final local selection uses a declared measured-development rule; freeze the winner before fresh held-out baseline/candidate evaluation, with no feedback from held-out tasks into search.
    • Account for proposal, gate, judge, and benchmark work exactly once, including failures. Retain per-phase observations and benchmark task counts separately from kernel trial/evaluation counts. Replay recorded decisions without model or benchmark execution; an entirely failed search remains inspectable.
    • Deliver a short runnable example and documentation stating the sequential limitation. Positive live gains and the paper's reported savings are not prerequisites for the deterministic mechanism proof.

    Out of scope¶

    A built-in SIFT preset, changes to existing TreeSearch semantics, unrestricted self-modification, automatic promotion, and the full benchmark campaign. Create no placeholder example tree or speculative runtime protocol before its gate.

    Milestone 11: trusted concurrency and distribution¶

    Status: Design—not shipped. The complete trusted-worker system remains the deliverable of #10. M11.0–M11.2 are Shipped: the design, concurrency-ready fold, durable work broker, dispatcher, and generational cohorts. M11.3 is Shipped with opt-in worker processes; distributed mode without a process backend still executes one call at a time. Administration, load validation, and the canonical demonstration remain below. The programming model owns backend selection; the M11 design owns the detailed consistency model, work state machine, and compatibility rules. The worker-process verification record separates the stabilization baseline from final stack integration evidence.

    Concurrency scope¶

    Admit only search policies declaring the cohort capability and passing its conformance suite; BestOfN is the only shipped example. Experiments declare neither pushed context nor pull experience, and only trial/evaluation counts may have finite budget ceilings. Population search does not gain concurrency. Paid concurrency depends on #206. Unsupported declarations raise CapabilityError at distributed start. The environment fingerprint is a worker's property, not a declaration, so it is checked when a worker is ADMITTED, and refuses that worker rather than the run.

    Remaining slices¶

    Slice Boundary

    M11.1 / #200 — Shipped Concurrency-ready fold and cohort writer; existing durable fixtures remain byte-identical.
    M11.2 / #201 — Shipped Cohort producer, durable work table, leases, fences, retries, terminal facts and duplicate exemption; single-process distributed resume rolls the epoch over.
    M11.3 / #202 — Shipped Cross-process claiming, worker submission returning Duplicate or Stale, and the deterministic-abort split: a resumed run reads the cause already recorded for the row's current attempt at the completion stage, ends the item on a deterministic one, and re-runs a transient one until the retry bound ends it.     M11.4 / #203 Trusted-worker administration, capability and capacity matching.

In-memory storage is its deterministic test double. Stores from before M11.2 require an explicit writable Storage.durable(...) migration before read-only access or browser inspection; keep that consequence visible in release notes.

    M11.3's first slice, #329, ships the durable prerequisites: input resolution before claiming, deterministic completion-abort recovery, inline lease renewal and dispatcher fencing. The event loop and worker submission belong to #341; worker processes belong to #353. Issue #202 remains open until those slices meet its cross-process gate.

    Acceptance of concurrent execution¶

    Demonstrate several processes claiming leased, count-bounded work, finishing out of wall-clock order, with one expired lease and one duplicate result. Preserve one logical trial across delivery attempts and exactly one accepted outcome.

    • Exercise competing claims, renewal/expiry races, cancellation, and capacity limits, including two claims exceeding one worker's declared capacity.
    • Reject stale and duplicate effects; terminate workers during proposal and evaluation and reconstruct the same authoritative state.
    • Derive exact budget admission and settlement from committed events; consumption is exact over accepted completions.
    • Rebuild after interleaved events. Cohort barriers expose the same completed result set regardless of arrival order. Recorded random choices and decisions replay; changed outcomes or abandoned attempts may change the trajectory.
    • Keep accepted outcomes, evaluations and promotion authoritative, while documenting any staleness in heuristic statistics.
    • Load-test simulated trusted workers before paid agent fleets.

    Untrusted community execution, Byzantine workers, public federation, multi-dispatcher availability/failover, and distributed experience are outside this gate. Local and distributed modes retain the same distinct domain identities.

    Pre-1.0 release policy¶

    The September 18, 2026 decision supersedes the former through-1.x promises for keyword run, dictionary CLI factories and preset defaults. Before 1.0, minor releases may make documented coordinated API changes; patches preserve the public API. No intermediate compatibility release or permanent legacy dispatch mode is required. The release inventory selects actual changes: keyword run and dictionary factories remain in 0.2.

    Supported historical formats remain readable. Schema migration is explicitly writable where needed. Resume requires verified compatible source and the execution mode's environment guarantees; API compatibility alone never promises cross-version continuation. Retain the old package/environment for historical execution when the current verifier refuses it.

    Milestone 12: contributed and federated network¶

    Status: Design—not shipped. #11 depends on M11. Two installations should exchange a signed, policy-filtered experience bundle, verify provenance and causal closure, independently evaluate promotion candidates, and process later retractions. The reserved example is examples/research/federated_exchange/; no placeholder implementation is needed.

    Acceptance must cover tampering, signatures/digests/schemas, redacted private ancestors, duplicate import idempotency, schema negotiation, conflicting evaluations, retraction propagation and independent verification. Import cannot widen source permissions or receiving trust; imported evaluations are evidence, not automatic promotion. Preserve licensing, attribution and embargo restrictions.

    Threat-model code execution, evaluator collusion, poisoning, sybils, reward hacking and correlated replication separately. Token economies, unrestricted peer-to-peer execution, global consensus, container-only security claims and scientific validity without domain evidence remain outside scope. See the network direction for rationale.

    Purpose¶

    Build a declarative library for evaluated evolution over versioned artifacts, then reuse the same boundaries to evaluate improvement procedures. Future scientific, search and meta-evolution directions do not authorize runtime structure before their acceptance gate.

    Development rules¶

    Follow repository discipline: trace a demonstrated requirement, implement its smallest complete vertical slice, and update focused tests, examples and current contracts together.

    Common definition of done¶

    A completed slice demonstrates correct behavior, deterministic replay where promised, exact accounting, typed failures, independent evaluation and preserved lineage/authority. Components stay replaceable without coordinator special cases; the ordinary callable path stays small. The repository completion check owns these shared rules rather than repeating them in every closed milestone.

    Local v1 functionality is shipped through M10. The active author API gate above owns the next coordinated package release; M11 and M12 own future concurrency and federation. Capability availability, release publication and evidence of model quality are separate claims; see current status.

    Milestone 7: generality proof and local v1¶

    Milestone 8: harness evolution¶

    Status: Shipped. A bounded harness can revise declared planner/context surfaces while fixed evaluators run fresh held-out episodes under equal budgets.     Milestone 8.7: audited prior-candidate source inspection¶

    Milestone 9: policy artifacts and meta-evolution¶

    Status: Shipped. Candidate policies can be evaluated by bounded inner searches while the outer evaluator, allowances and promotion stay independent. The policy-evolution guide and nested-evaluation comparison explain the runnable scope, retained inner histories and explicit cost forwarding.

    Status: Shipped. The ADRS-inspired fixture evaluates a bounded scheduler and retains a separate post-search comparison, typed failures and exact scenario accounting. It proves a local simulator result using existing seams, not live-model search or production speedups.

    Architecture gate across all milestones¶

    A new domain supplies artifact semantics, proposer, evaluator, search/context and optional adapters without a coordinator branch or weakened authority. Introduce a protocol seam only for a demonstrated acceptance requirement; future milestones are direction, not permission to pre-create their package tree.
